================================================================================
SOFTWARE REQUIREMENTS SPECIFICATION
FeedBoard - Multi-Tenant Feedback & Roadmap Platform
Version 1.2
================================================================================

--------------------------------------------------------------------------------
1. INTRODUCTION
--------------------------------------------------------------------------------

1.1 Purpose
    This document specifies the requirements for FeedBoard, a multi-tenant SaaS
    platform that lets companies collect product feedback from their users,
    prioritize it through voting, and communicate progress through a public
    roadmap and changelog.

1.2 Scope
    Each customer (tenant) receives a branded public portal where their end
    users submit and upvote feedback, and a private admin dashboard where the
    tenant's team triages and manages that feedback, plans a roadmap, and
    publishes release notes. The system is delivered as a web application
    backed by a stateless REST API and a relational database.

1.3 Definitions
    Tenant        An isolated customer workspace.
    Visitor/Guest An unauthenticated end user on a tenant's public portal.
    Member        An authenticated tenant team member (owner or user).
    Admin         A platform operator (the app owner) with super-access across
                  every workspace; a ROLE on a regular account (the same account
                  can also be a tenant user), entered via the admin sign-in.
    Portal        The public, tenant-branded surface (board, roadmap, changelog).
    Dashboard     The private, authenticated workspace application.

--------------------------------------------------------------------------------
2. OVERALL DESCRIPTION
--------------------------------------------------------------------------------

2.1 Product Perspective
    - Frontend: Next.js (App Router) web application; communicates only with the
      REST API.
    - Backend: Node.js/Express REST API over a MySQL database (raw SQL, no ORM).
    - One codebase serves two surfaces: the authenticated dashboard and the
      public, per-tenant portal.

2.2 User Roles & Permissions
    There are exactly three roles.
    - Visitor/Guest: view a tenant portal, submit feedback (name optional, but a
      contact email is required for follow-up), and upvote posts. No account
      required.
    - User: an authenticated workspace member with baseline access (Profile only
      in settings). Members join by invitation.
    - Owner: the workspace administrator — manages team, tags, branding, billing,
      and feedback deletion. A workspace has
      exactly ONE owner (its creator); everyone else is a member. An account may
      therefore own some workspaces and be a member of others; the two are shown
      separately in the workspace switcher.
    - Admin (platform): the app operator. A ROLE on a regular account (the same
      account can be a tenant user too); signs in through a dedicated admin
      sign-in that grants that role, and has super-access over every
      workspace and user through the Admin Panel (see 3.11). "Admin" is never a
      role inside a workspace.

2.3 Multi-Tenancy
    - Each tenant is reachable at <subdomain>.<root-domain>.
    - All data is isolated by tenant; every query is tenant-scoped.
    - Reserved subdomains (www, app, admin, ...) are never tenants.

2.4 Operating Environment
    - Modern evergreen web browsers.
    - Cloud-hosted application and API; managed MySQL; wildcard DNS
      (*.<root-domain>).

3. FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

3.1 Authentication & Accounts
    - Email/password authentication using JWT bearer tokens.
    - The session carries the user identity, tenant, and role.
    - Profile management: name, contact, avatar upload, and password change.
    FR-G1  Google sign-in  A visitor may create an account or sign in with
                          "Continue with Google", offered on both the sign-in and
                          sign-up pages alongside the email form. The system
                          requests only the user's basic profile — identifier,
                          email address, name and picture — and never receives
                          their Google password.
                          Google must report the address as VERIFIED. An
                          unverified address is refused, because accounts are
                          matched by email and accepting one would let a person
                          claim an account that is not theirs.
                          The Google identity, not the email address, is what
                          identifies the person on return visits, so changing the
                          address on their Google account keeps them signed in to
                          the same FeedBoard account.
                          A first-time user is created WITHOUT a workspace and
                          WITHOUT a password, exactly as an email sign-up is, and
                          continues to workspace creation. Signing in this way
                          obeys the same single-session rule as a password sign-in
                          (FR-S1), including the "sign out other devices" option.
    FR-PR1 Password reset  A user who has forgotten their password can request a
                          reset from the sign-in page by entering their email. The
                          system responds identically whether or not the email is
                          registered (it never reveals which addresses have
                          accounts) and, when it matches an account, emails a
                          single-use link valid for one hour. Opening the link
                          lets the user set a new password; the link cannot be
                          reused or used after it expires. Completing a reset
                          signs the account out of all devices, so it must be
                          signed in again with the new password.
                          This flow also serves accounts created through Google,
                          which have no password: it is how such an account SETS
                          one. Without it, signing up with Google would be a
                          one-way door — losing access to the Google account
                          would mean losing the workspace.
    FR-D1  Delete account  A user may permanently delete their account from
                          Settings. Before anything happens they are shown exactly
                          what will be lost, and must re-enter their password and
                          type a confirmation word. An account created through
                          Google has no password to re-enter, so it is asked only
                          for the confirmation word — otherwise it could never be
                          deleted. Workspaces they OWN are deleted
                          with the account (all feedback, roadmap, changelog and
                          member access; any subscription is cancelled), because a
                          workspace has exactly one owner and cannot be
                          transferred. Workspaces they merely joined are retained:
                          only their membership is removed, and their posts and
                          comments there remain but become anonymous.
    FR-I1  Invitations .. A workspace owner invites teammates by email address.
                          The address is validated (format + mail-domain lookup)
                          before sending. The invitee receives a branded email with
                          a secure link that is valid for 7 days and can be used
                          only once; the owner can revoke a pending invitation,
                          which disables its link immediately. Accepting as a new
                          person opens a sign-up dialog (email fixed), after which
                          they create their own workspace and are taken to the
                          workspace that invited them. An existing account must be
                          signed in as the invited address and joins in one step.
                          Invitees always join as members. Invitations count
                          against the plan's team-member limit (see FR-B5).
    FR-S1  Single-session  On the Free and Pro plans an account may be signed in
           login .......... on only ONE device or browser at a time. Attempting to
                          sign in elsewhere while a session is live is refused, and
                          the user is told to sign out on the other device first
                          (with the option to upgrade). Because the password was
                          correct, they are also offered a one-click "this is me —
                          sign out other devices and sign in here" takeover that
                          ends the other sessions and signs them in. Signing out
                          releases the session immediately. A session that has been
                          inactive for 15 minutes is also treated as abandoned —
                          the next sign-in takes it over and ends the old one — so
                          closing the browser without signing out never locks a
                          user out. Once
                          a session ends, that device is signed out on its next
                          action rather than being left in a broken state.
                          Switching workspaces does not count as a new device.
                          BUSINESS plans permit unlimited concurrent devices,
                          browsers and tabs (see FR-B5).
    FR-S2  Single tab .... On single-session plans, opening the dashboard in a
                          second tab or window of the same browser shows a blocking
                          notice rather than a second working copy, with an option
                          to upgrade. Closing the original frees the other tab
                          automatically.
    FR-W1  Workspaces ... One account (email) may belong to multiple workspaces
                          (tenants), and only ever sees workspaces it belongs to.
                          A new account starts with NO workspace and is sent to
                          onboarding to create its first (name, subdomain,
                          optional website). Users can create additional
                          workspaces and switch the active one from the sidebar;
                          the dashboard re-scopes to the selection without a
                          re-login. Each new workspace is owned by its creator and
                          seeded with the default, status-linked roadmap columns.
                          Each workspace subdomain must be unique; the create
                          forms validate availability live before submission.
    FR-W2  Workspace .... The number of workspaces an account may OWN and be a
           limits ....... MEMBER of is capped by the account's tier — its own
                          subscription plan (an account that never subscribed is
                          treated as Free). Free may own 1 and join 1, Pro
                          own 3 and join 3, and Business unlimited of each. A first
                          workspace is always allowed (an account owns none yet);
                          beyond the cap, creating or accepting an invitation is
                          refused with an upgrade prompt. To raise the cap,
                          upgrade the account to Pro or Business.

3.2 Public Portal (Visitors)
    The portal is the primary channel for collecting feedback.
    - Branded header (tenant logo, or a brand-colored initial fallback) using
      the tenant's primary color.
    FR-P1  Board ........ Browse feedback posts with vote counts, tags, status,
                          and comment counts. Sortable by newest, oldest, most
                          upvoted, or least upvoted (pinned posts stay on top).
                          Filterable by status via tabs — All, Open, Planned, In
                          Progress, Completed, Rejected. Rejected posts show a
                          Rejected status badge rather than being hidden, and
                          voting/commenting on them work the same as any other
                          post.
    FR-P2  Submit ....... Any visitor may create a post (title and a contact
                          email required; details, type and name optional). The
                          email is mandatory so the team can reach the submitter
                          with updates on their post; it is never shown publicly.
                          This applies to every submitter, signed in or not: a
                          post records the contact details given on the form and
                          is not attributed to an account. Posting is available
                          on every plan, including to the board's own owner.
                          On workspaces whose plan includes attachments
                          (see FR-A1), the submit form also lets the visitor
                          attach photos or a short video.
    FR-P3  Vote ......... Any visitor may upvote/remove an upvote. Voting is
                          limited to one vote per browser per post via a
                          persistent cookie identifier; no account required.
                          The public board is the ONLY place a vote can be cast:
                          votes measure demand among a workspace's users, so the
                          workspace's own owner and team members cannot upvote
                          (see FR-F7).
    FR-P4  Post detail .. Read a post and its threaded comments.
    FR-P5  Comment ...... Any visitor may add a comment, or a threaded reply to a
                          comment, on a post — anonymously or with an optional
                          name/email (the name is remembered for the session). A
                          logged-in user's comment/post is attributed to them,
                          showing their name and profile picture instead of a
                          guest identity. An anonymous guest who leaves no name is
                          shown with a stable, friendly pseudonym and a coloured
                          incognito avatar (consistent across that guest's
                          posts/comments, distinct from other guests, and clearly
                          marked as anonymous) rather than a uniform "Anonymous".
    FR-P6  Share ........ Each post has a public share control: copy link, the
                          device's native share sheet, and one-click social
                          intents (X, LinkedIn, Facebook, WhatsApp, Email). Shared
                          links unfurl with a rich preview (Open Graph / Twitter
                          Card) including a branded, per-post preview image.
    FR-P7  Own content .. A logged-in user may edit or delete their own posts and
                          comments from the public portal (owner-only; enforced
                          server-side). Guests cannot edit/delete.
    FR-P8  Get a board .. Every tenant portal carries a FeedBoard growth CTA
                          inviting visitors to create their own feedback board
                          (links to sign-up): a prominent banner at the very top
                          of every portal page. It is styled in FeedBoard's own
                          brand so it reads as our promotion, distinct from the
                          tenant's content. Shown once per page — the footer
                          does not repeat it.
    FR-P9  Verified ..... A comment authored by a platform administrator shows a
                          "Verified admin" tick beside the name, so visitors can
                          recognise an official reply from the platform's team.
                          The mark is derived from the platform-admin role on the
                          account, not from a display name. The administrator's
                          avatar is the product's own app icon (also their profile
                          picture and the official feedback board's logo), so an
                          official reply is visually branded as coming from the
                          platform.
    FR-P10 Identity ..... POSTING AND COMMENTING ARE AVAILABLE ON EVERY PLAN,
                          including to the board's own owner. What a paid plan
                          buys is the VERIFIED OWNER BADGE a comment may carry,
                          never the right to take part.
                          When commenting on a public board, a logged-in author
                          may choose the identity shown. EVERY logged-in user —
                          the board's own owner included, on any plan — may post
                          as THEMSELVES or ANONYMOUSLY (as a guest, with no name
                          and no tick), so anyone may always comment without
                          revealing who they are. Posting anonymously is never
                          charged for: it withholds an identity rather than
                          granting one.
                          The BADGED identities are what require a paid plan. On
                          Pro and above the board owner may appear as
                          "Name (Owner)" with a verified tick and their profile
                          picture; on Business they may instead choose a generic
                          "Owner" with a tick (real name withheld, shown with the
                          workspace's own logo as the avatar). On the free plan
                          the owner comments under their own plain name, with no
                          tick. Gating is enforced server-side,
                          not just in the UI, and requesting an identity the plan
                          does not include falls back to the author's plain name
                          rather than rejecting the comment. The choice applies to
                          the comment and its replies, on both the public portal
                          and (except anonymous) the dashboard.
    FR-A1  Attachments .. On workspaces whose plan permits it (Pro and above; see
                          FR-B5), a feedback post may carry up to three photo or
                          short-video attachments. Attaching is offered on both
                          the public submit form and the dashboard's create-post
                          form; on plans without it the control is hidden and an
                          upgrade prompt is shown. Images are limited to 10MB and
                          video to 50MB each (duration is bounded by file size).
                          Attachments display on the post detail — photos in a
                          thumbnail grid that opens full size, video inline with
                          playback controls — and posts with media are flagged on
                          the board. Uploads are validated for type and size and
                          gated by plan on the server, independently of the UI.
    - The public portal exposes the feedback board and a public CHANGELOG (a
      "Changelog" tab in the portal nav, listing only PUBLISHED entries). The
      roadmap is NOT public — its portal route redirects to the board and it is
      managed in the admin dashboard.
    - Public responses expose only safe fields; author and guest emails are
      never returned on public routes.

3.3 Feedback Management (Dashboard)
    Feedback originates from end users on the public portal. The dashboard is
    for triage and management; the team does not author new posts here.
    FR-F1  List ......... Search and filter by status, type, and tag.
    FR-F2  Maintain ..... The team does NOT edit the text of a user's feedback —
                          the content belongs to its author. Triage is done via
                          status, tags, pin, and duplicate marking (FR-F3..F6).
                          Deleting a feedback post is restricted to the workspace
                          owner and requires a paid plan (Pro or higher); it is
                          enforced server-side and the control is hidden/locked
                          otherwise (see FR-B5).
    FR-F3  Status ....... Set status: open, planned, in progress, or completed
                          (the "closed" status is not offered in the picker).
    FR-F8  Reject ....... The team can REJECT feedback it has declined — as a
                          bulk action on the Open tab (alongside "Send to
                          Roadmap") or from a post's detail view. Rejected
                          feedback appears in its own "Rejected" tab and in the
                          "All" tab, both in the dashboard and on the public
                          portal (shown with a Rejected badge, not hidden).
                          From the Rejected tab (or the post's detail view) it
                          can be RESTORED to Open.
    FR-F9  Contact ...... On a paid plan (Pro or higher) the workspace OWNER can
           submitter ..... see the email address of the person who submitted a
                          piece of feedback, and — once the feedback is marked
                          COMPLETED — send them an automated "your feedback is
                          implemented" email. The send is recorded and can be
                          re-sent. On the Free plan the email is not shown and the
                          action is unavailable (an upgrade prompt is shown);
                          enforced server-side. The email address is never exposed
                          on the public portal.
    FR-F4  Pin .......... Pin important posts to the top.
    FR-F5  Tags ......... Assign or remove tags.
    FR-F6  Duplicates ... Mark a post as a duplicate, with suggested matches.
    FR-F7  Engage ....... Full post view with tags, duplicates, and the post's
                          discussion, where a team member can post a comment or a
                          threaded reply (attributed to their account; a platform
                          administrator's reply carries the verified mark of
                          FR-P9). The team cannot upvote: vote counts are shown as
                          a read-only tally on both the list and the post view,
                          because votes measure demand among the workspace's users
                          and are cast only from the public board (see FR-P3).
    FR-F10 Promote ...... From the Open tab, select one, several, or all posts
                          and add them to a chosen roadmap column in a single
                          action (with an optional target date). Adding a post to
                          a status column also sets its status; posts already on
                          the roadmap are skipped.
    - Guest submissions appear as "Anonymous" (or the supplied name); the team
      can see a guest's email, when provided, for follow-up.

3.4 Roadmap
    FR-R1  Columns ...... Fixed. Each workspace is seeded with the default
                          status-linked columns (Planned, In Progress, Completed);
                          they cannot be created, renamed or deleted from the
                          board. Their labels are the shared status labels, so the
                          roadmap always agrees with the status shown on the
                          feedback board, the public portal and analytics.
    FR-R2  Items ........ Add a post to a column with an optional target date;
                          move items between columns by drag-and-drop; remove items.
    FR-R3  Status sync .. Columns whose key matches a post status (planned,
                          in_progress, completed, ...) are linked to that status:
                          moving an item into such a column sets the post's status,
                          and changing a post's status moves its roadmap item into
                          the matching column. Removing (dismissing) a post from the
                          roadmap returns it to the Open state, so it reappears in
                          the Open tab. The roadmap and the feedback board's status
                          tabs therefore stay consistent.

3.5 Changelog
    FR-C1  Authoring .... Create and edit entries with Markdown content.
    FR-C2  Publishing ... Save as draft or publish; only published entries are
                          visible on the portal.

3.6 Notifications
    FR-N1  In-app notifications with an unread count and deep links to the
           referenced post or changelog; mark read, mark all read, and delete.
           Notification text is rendered in the READER's interface language,
           not the language in effect when the event occurred (see 3.12).
    FR-N3  In-app activity — every team member of a workspace receives an in-app
           notification when new feedback is posted on the public board and when
           a comment is added to feedback, each deep-linking to the post. The
           person who took the action (if a team member) is not notified of their
           own activity. Generation never blocks or fails the visitor's action.
    FR-N2  Email — the workspace owner is emailed each time new feedback is
           posted on their public board. The message shows the type, author,
           title and an excerpt, and links straight to the post in the dashboard.
           Owners are not emailed about their own submissions. Delivery never
           blocks or fails the visitor's submission.

3.7 Administration (Settings)
    Tabs: Profile, Team (roles), Tags, Branding (company logo, workspace name,
    and the workspace subdomain — which the owner can change, validated for
    format and uniqueness), and Billing. Owner-only tabs are gated by role;
    updating workspace settings is restricted to the workspace's own owner.

3.8 Analytics
    FR-AN1 Overview of totals, status/type breakdowns, and a recent-activity trend.

3.9 Platform Services
    File uploads (avatars, workspace logo, and feedback photo/video attachments)
    served from the API origin.

3.9a Support Chat
    A live chat between a workspace user and the platform administrator.
    FR-SC1 Contact ...... Every signed-in user (any role, any plan) has a
                          "Contact support" launcher on every dashboard page that
                          opens a chat with the platform admin.
    FR-SC2 Session ...... A conversation is a session. A user has at most one open
                          session at a time; contacting support resumes the open
                          one or starts a new one.
    FR-SC3 Exchange ..... Both sides send text messages; new messages appear
                          within a few seconds. Each side sees an unread indicator
                          for messages awaiting their attention.
    FR-SC4 Close ........ The admin ends a session when the matter is resolved.
                          After closing, the USER can no longer view or reply to
                          that session (a new one must be started), while the ADMIN
                          retains the full transcript indefinitely, browsable under
                          a Closed list. Transcripts survive even if the user later
                          deletes their account.

3.10 Billing & Subscriptions
    A subscription belongs to the USER ACCOUNT, not an individual workspace:
    a user pays once and the plan covers EVERY workspace they own (a new
    workspace an account creates inherits the account's current plan). Team-size
    (seat) limits still apply per workspace. Payment is processed by a Merchant
    of Record (Paddle) via an overlay checkout and a customer portal — no card
    data is stored by the platform. (The provider is configurable; a Stripe
    implementation is retained as an alternative.) A downgrade takes effect at the
    END of the current paid period — the customer keeps their current plan until
    then, with no charge and no refund; an upgrade charges the exact prorated
    difference now, previewed before it is confirmed. Moving from yearly to monthly
    billing is likewise scheduled for the period end: the paid year is kept in full
    and monthly billing begins on that date. Moving from monthly to yearly billing
    as part of a tier downgrade is not offered — the tier and the billing interval
    are changed one at a time.
    FR-B1  Plans ........ Three tiers: Free ($0), Pro ($10/mo), and Business
                          ($15/mo). Paid tiers may be billed MONTHLY or YEARLY;
                          yearly is ~20% cheaper, priced at a whole-dollar monthly
                          equivalent (Pro $8/mo = $96/yr, Business $12/mo =
                          $144/yr). Tiers and features are
                          presented on a public pricing page and on the dashboard
                          Billing tab, each with a Monthly/Yearly toggle. The
                          headline figure is ALWAYS a per-month price — on the
                          yearly interval, the per-month equivalent with a
                          "billed annually" note — never the annual total.
                          Pro and Business carry a small merchandising label
                          ("Popular" / "Best") beside the plan name.
    FR-B2  Subscribe .... From Free, an owner subscribes to a paid plan (monthly
                          or yearly) via the payment processor's checkout; on
                          success the plan and interval are updated.
    FR-B2b Buy on signup  Choosing a paid plan on the public pricing page carries
                          that choice through sign-up and workspace creation to a
                          payment step, and only then to the dashboard. The choice
                          travels as a single encrypted, expiring token in the web
                          address — it is never readable there, and cannot be
                          altered by editing the address bar, so nobody can change
                          which plan is about to be charged for. It is decrypted
                          and re-checked at each step rather than trusted, and a
                          token that fails verification simply means no plan was
                          chosen. The token never carries a price; the price is
                          determined when payment begins. Payment
                          necessarily follows workspace creation, because only a
                          workspace OWNER may purchase. Someone accepting an
                          invitation is never taken to payment: they join an
                          existing workspace as a member and members cannot buy.
                          Abandoning payment leaves a working free account and
                          workspace, and that exit is offered plainly. The payment
                          step states that taxes are calculated at checkout rather
                          than showing a total, because the processor is the
                          merchant of record and adds tax the platform does not
                          calculate. Yearly pricing is shown by default; an
                          existing subscriber always sees their own billing
                          interval first.
    FR-B2a Change plan .. An existing subscriber changes plan or interval FROM THE
                          BILLING TAB with correct PRORATION (not via the portal).
                          An UPGRADE first shows the exact prorated amount charged
                          now — only the difference, crediting the time already
                          paid for — then, on confirmation, charges it immediately.
                          A DOWNGRADE takes effect at the END of the paid period:
                          the higher tier is kept until then with no charge or
                          refund now; the scheduled change is shown and can be
                          cancelled. Applies equally to monthly and yearly, and to
                          switching interval on the same tier.
    FR-B3  Manage ....... The subscriber can CANCEL from the Billing tab in-app:
                          cancellation takes effect at the END of the paid period —
                          they keep the plan until then and are NOT charged again,
                          after which the account (and all the workspaces it owns)
                          reverts to Free. A cancellation can be RESUMED before the
                          period ends to keep the subscription. The Stripe Customer
                          Portal remains available for card updates.
    FR-B4  Sync ......... A Stripe webhook keeps the account plan and status in
                          sync with the subscription lifecycle, mirrored to every
                          workspace the account owns.
    FR-B5  Enforcement .. Paid capabilities are gated by plan: a Free workspace
                          cannot delete feedback posts, attach photos/video to
                          feedback, or contact/notify submitters, and is prompted
                          to upgrade. Deleting feedback and contacting submitters
                          additionally require the owner role.
                          Team size is capped by the plan's seat limit, counted
                          as members BESIDES the owner: Free allows the owner plus
                          2 team members, Pro the owner plus 5, and Business an
                          unlimited team. The cap is enforced when an invitation is
                          sent (current members + outstanding invites). The number
                          of workspaces an account may own and join is likewise
                          tier-capped (see FR-W2). CONCURRENT
                          DEVICES are also a plan capability: Free and Pro allow a
                          single active session at a time, while Business allows
                          unlimited devices, browsers and tabs (see FR-S1, FR-S2).
                          The plan is set only by Stripe (or an admin comp) and
                          cannot be changed directly by the client.
    FR-B6  Promo codes . Admins generate promo codes (see 3.11): percentage-off
                          codes (for any or a specific plan, backed by a discount on
                          the active payment processor) and free-plan comps (Pro/Business). An owner redeems a code
                          in the Billing tab — free-plan codes grant the plan
                          instantly with no charge, percentage-off codes apply at
                          checkout. Codes support a duration, a redemption limit,
                          and an expiry, and may be revoked.
    FR-B7  Offers ...... Admins set a promotional price on a paid plan for a chosen
                          billing cycle — MONTHLY or YEARLY (see 3.11) — optionally
                          time-bounded, and the price may include cents. A monthly
                          offer discounts the monthly price; a yearly offer discounts
                          the yearly total and REPLACES the built-in yearly discount
                          (it does not stack on it). While an offer is active, the
                          Billing tab and public pricing cards, when showing that
                          interval, draw the reference price with a diagonal
                          strikethrough beside the lower offer price (both quoted
                          per month — a yearly offer is struck through the plain
                          monthly list price) and a "save %" badge computed from
                          the two displayed figures, and the exact discount is
                          applied automatically at checkout. One active offer per
                          plan and cycle.
                          The offer's time window also decides how long a customer
                          KEEPS the offer price: a monthly offer running three
                          months bills the offer price for three monthly periods
                          and then the regular price, while a yearly offer taken
                          during the window covers that whole year. Both the
                          Billing tab and the pricing cards state this ("Offer
                          price for the first 3 months, then $10.00/mo") so a
                          temporary price is never presented as permanent.
                          An active offer is the plan's CURRENT price rather than a
                          new-customer deal: an existing subscriber whose renewal
                          falls during the window is billed the offer price too,
                          and the Billing tab tells them so. A customer already on
                          a promo code or an earlier offer keeps those terms.

3.11 Platform Administration (Admin Panel)
    A platform admin manages the entire platform from a dedicated panel.
    FR-AD1 Access ...... Platform admin is a role held by a regular account (the
                          same account can also be a tenant user). Signing in at
                          the dedicated admin sign-in checks that role and yields
                          an admin session (no workspace, routed to the Admin
                          Panel); the normal sign-in yields the user session.
    FR-AD2 Workspaces .. View every workspace (owner, plan, status, member/post
                          counts); rename, activate/deactivate, or delete. The
                          plan is shown READ-ONLY here (it is set per account —
                          see FR-AD2a). Open any workspace to moderate its feedback
                          posts — change status, pin/unpin, or delete — and delete
                          any of a post's comments (comment text is not editable —
                          it belongs to its author).
    FR-AD2a Accounts ... View every billing account (email, owner name, the
                          workspaces it owns, and its plan); grant/revoke a plan
                          (a comp — a paid plan with no charge) for the WHOLE
                          account, so it applies to every workspace the account
                          owns. A grant lets the admin choose a duration —
                          Lifetime or a fixed number of months, after which the
                          account automatically reverts to Free. Granting a comp
                          also cancels any live paid subscription so the account is
                          no longer charged for its previous plan.
    FR-AD3 Users ....... View and search all users across workspaces; change role
                          (owner/user), activate/deactivate, reset the password,
                          or delete. A listing entry is one workspace membership,
                          so role and active state apply to that membership,
                          while the password and deletion apply to the whole
                          ACCOUNT. Resetting the password sets it for every
                          workspace the account belongs to and signs it out of
                          all devices. Deleting removes the account exactly as
                          the account holder's own deletion would (FR-D1): any
                          paid subscription is cancelled, owned workspaces and
                          their content are deleted, joined workspaces are
                          retained with the person's content anonymised, and the
                          billing record, sessions and pending invitations are
                          erased. Before deleting, the admin is shown precisely
                          what will be destroyed. An account holding the
                          platform-admin role cannot be deleted here; the role
                          must be revoked first (FR-AD4).
    FR-AD4 Admins ...... List admins and grant or revoke the platform-admin role
                          on accounts (revoking never deletes the underlying user
                          account; an admin cannot revoke their own role).
    FR-AD5 Overview .... Platform-wide counts (workspaces, users, posts, paid
                          subscriptions, promo redemptions) and a plan breakdown.
    FR-AD6 Promo/Offers  Generate and revoke promo codes, and create/end
                          promotional plan offers (FR-B6, FR-B7).
    FR-AD7 Support ...... Answer users' support chats from a queue (open first,
                          with unread indicators), reply in real time, and close a
                          session when resolved. Closed sessions stay readable as
                          history (see FR-SC1–FR-SC4).


3.12 LOCALIZATION (INTERNATIONALIZATION)
--------------------------------------------------------------------------------

    FR-L1  Languages .... The entire user interface — marketing site, dashboard,
                          public portals, and Admin Panel — is available in 8
                          major EU languages: English, German, French, Spanish,
                          Italian, Portuguese, Dutch, and Polish. English is the
                          default and the fallback for any untranslated string.
    FR-L2  Selection .... A language selector appears in every navigation bar,
                          including the public portal header (portal visitors get
                          their own control, tinted with the tenant's brand
                          color). The choice persists across visits and applies
                          immediately without a reload of context.
    FR-L3  Depth ........ Localization covers static text, validation and error
                          messages (including API responses), dates and times
                          (formatted per the selected language, in the viewer's
                          timezone), and grammatical plurals — including
                          languages with plural categories English lacks.
    FR-L4  Stored text .. Text generated when an event occurs (e.g. an activity
                          notification) is stored with its structured parts so it
                          can be rendered later in whatever language its READER
                          uses, with English as the fallback for legacy records.

3.13 PRODUCT FEEDBACK (SELF-HOSTED BOARD)
--------------------------------------------------------------------------------

    FR-PF1 Own board .... FeedBoard operates a public feedback board for the
                          product itself. It is a standard workspace (no special
                          casing), owned by the platform administrator's own
                          account, so it is managed with the same dashboard and
                          moderation tools as any customer workspace.
    FR-PF2 Open access .. Any visitor may submit product feedback, comment, and
                          vote without an account; a contact email is required
                          so the team can respond. A signed-in user's submission
                          is attributed to their account and stays editable by
                          them.
    FR-PF3 Entry points . Signed-in users reach the board from a Give feedback
                          item in the dashboard sidebar; signed-out visitors
                          reach it from a link in the marketing site footer.

3.14 LEGAL DOCUMENTS

    FR-LG1 Documents .... Four public documents are published: Terms of Service,
                          Privacy Policy, Cookie Policy and Refund Policy. Each
                          shows a last-updated date and links to the other three.

    FR-LG2 Placement .... Linked from the marketing site footer, the public
                          portal footer (so board visitors can reach them from a
                          tenant subdomain) and the sign-up form, which states
                          that creating an account accepts the Terms and Privacy
                          Policy.

    FR-LG3 Language ..... The documents are published in English only and each
                          states that English is the authoritative version;
                          they are deliberately excluded from the interface
                          translation described in 3.12, because a mistranslated
                          liability or refund clause carries real risk.

    FR-LG4 Accuracy ..... The documents describe the system as built — session
                          and visitor cookies with their real names and
                          lifetimes, the single-device limit on Free and Pro,
                          guest submitter emails being stored but never shown
                          publicly, payment data being held only by the payment
                          processor, offers applying to renewals, proration on upgrade versus scheduled
                          downgrade, and the effect of account deletion on owned
                          versus joined workspaces. A change to any of those
                          behaviours requires the corresponding document to be
                          updated in the same change.

    FR-LG5 Operator data  Entity name, registered address, governing
                          jurisdiction and contact addresses are held in one
                          configuration module. Values left unset render as a
                          visible placeholder so an incomplete document cannot
                          be published unnoticed.

    FR-LG6 Refunds ...... Paid periods are non-refundable. Cancellation marks the
                          subscription to end at the close of the current period:
                          access continues to that date, no further charge is
                          made, and no proportion of the paid period is returned.
                          Two exceptions are documented: correction of a billing
                          error (duplicate charge, charge after cancellation took
                          effect, or a charge for a plan or interval other than
                          the one confirmed), and the remedy owed if a paid plan
                          is materially reduced during a prepaid term. Mandatory
                          consumer rights prevail where they apply.

4. EXTERNAL INTERFACES
--------------------------------------------------------------------------------

4.1 REST API
    - JSON over HTTP; responses share a { status, message, data } envelope.
    - Authenticated routes require Authorization: Bearer <token>.
    - Public portal routes (/public/*) are unauthenticated and tenant-scoped by
      subdomain.

4.2 User Interface
    - Portal: board, post detail, roadmap, changelog.
    - Dashboard: overview, feedback, roadmap, changelog, notifications, settings.
    - Admin Panel: overview, workspaces, users, admins, promo codes, offers.
    - A single, consistent visual system (see 5.5).

--------------------------------------------------------------------------------
5. NON-FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

5.1 Performance .... Interactions feel instant; route transitions stream a
                     skeleton; API responses are compressed. Database access is
                     pooled, hot read-only lookups are cached in-process with a
                     short expiry, and list endpoints aggregate related counts in
                     batched queries rather than per row.
5.2 Security ....... HTTPS; JWT authentication; server-side validation; strict
                     tenant isolation; no private fields (e.g. emails) on public
                     routes; hardened HTTP response headers.
5.3 Scalability .... Stateless API over a connection-pooled database; designed
                     for many tenants and wildcard-subdomain routing. The API
                     runs as multiple worker processes behind a load balancer to
                     use all available CPU cores.
5.4 Availability ... Target 99.9% uptime. Workers restart automatically on
                     failure; shutdown is graceful (in-flight requests complete
                     and database connections are released) so deploys and
                     restarts do not drop traffic.
5.6 Abuse
    resistance ..... Request rates are limited per client, with stricter limits
                     on sign-in attempts, unauthenticated submissions, and
                     actions that send email or contact payment providers.
                     Request size, page size, and connection lifetime are all
                     bounded so that no single request or slow client can
                     exhaust server memory or connections.
5.5 Usability ...... Light-only theme; one type family; a rose product palette
                     with a per-tenant brand color on each portal; consistent
                     forms, dialogs, and dropdowns.

6. DATA MODEL (principal tables)
--------------------------------------------------------------------------------

    tenants, users (role owner/user), invitations, posts (with guest submitter
    fields), post_attachments (photo/video on feedback, Pro+), votes
    (supporting guest voting), comments, tags, post_tags,
    roadmap_columns, roadmap_items, changelog_entries, notifications (with
    structured, reader-language-renderable text — FR-L4), support_sessions and
    support_messages (FR-SC1..SC4), oauth_accounts. All feature tables are
    scoped by tenant. user_sessions records the active device sessions behind
    an account and backs single-session login (FR-S1). The platform-admin role is a
    flag on the users account (users.is_platform_admin). Platform-level (not
    tenant-scoped): promo_codes,
    promo_redemptions, and offers. (api_keys, audit_logs, and integrations
    exist in the schema but back no current feature — the third-party
    integrations feature was cancelled; see 8. Future Enhancements.)
