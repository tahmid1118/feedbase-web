## Architecture

### Overview

FeedBoard is a multi-tenant SaaS feedback platform (a UserJot-style product). The Next.js frontend communicates exclusively with a backend REST API on `http://localhost:4560` — there is **no database access from this codebase**. The backend is a separate repo at `D:\Development\Backend\feedbase-backend` (with its own CLAUDE.md).

### Path Aliases

`@/*` resolves to the **project root** (not `src/`). All imports use this alias.

### App Router Structure

```
app/
├── (auth)/               # Unauthenticated layout — login, signup
├── api/auth/             # NextAuth route handlers + registration proxy
├── dashboard/            # Protected (admin) app — redirects to /login if no session
│   ├── feedback/         # Feedback list + [id] detail page
│   ├── roadmap/          # Kanban board (drag & drop via @dnd-kit)
│   ├── changelog/        # Release notes (markdown)
│   ├── notifications/    # User notifications
│   └── settings/         # 5 tabs: profile, team, tags, branding, billing (owner-only tabs gated)
├── admin/                # PLATFORM Admin Panel — overview, workspaces, users, admins, promo-codes, offers (isAdmin only)
├── portal/[tenant]/      # PUBLIC per-tenant portal — board, post, roadmap, changelog (read-only, unauthenticated)
├── legal/                # Terms, Privacy, Cookie + Refund policies (public, English-only)
└── page.tsx              # Landing page
```

Dashboard pages are `"use client"` and read the access token from `useSession()`. The dashboard layout (`app/dashboard/layout.tsx`) is a Server Component that gates auth via `await auth()`.

### Multi-tenant subdomain portal

- **`proxy.ts`** (project root — Next 16's `proxy` convention, which **replaced `middleware`**) reads the request host and rewrites `<tenant>.<root>/<path>` → `/portal/<tenant>/<path>`. **Only subdomains of the root domain route to a portal**; any other host (and reserved subdomains `www`, `app`, `admin`, …) falls through to the admin app. Custom domains are **not** supported. Root domain comes from `NEXT_PUBLIC_ROOT_DOMAIN` (default `localhost:3000`).
- **`app/portal/[tenant]/`** renders public pages from **`lib/api/public.ts`** — an unauthenticated **server-side** client that hits the backend `/public/*` routes. Only safe fields are exposed (no author emails; drafts hidden). Internal links use `/portal/<tenant>/…` so they work both on a subdomain and via the direct path.
- **Portal nav** (`components/portal/portal-nav.tsx`, in the portal layout header) has **Board** and **Changelog** tabs. The public **changelog** (`app/portal/[tenant]/changelog`, list + `[id]` detail) shows only **published** entries (backend `getPublicChangelog` filters `is_published = 1`). The **roadmap** portal route stays a redirect-to-board (not public). Nav/detail links use absolute `/portal/<tenant>/…` hrefs — the proxy passes any `/portal/…` path straight through, so they work on a subdomain and via the direct path; the active tab is derived from the pathname suffix (client `usePathname`).
- The board has **status filter tabs** (`components/portal/board-tabs.tsx`) — **All / Open / Planned / In Progress / Completed** — mirroring the dashboard's pill tabs. **"Rejected" is deliberately absent** (rejected posts are always excluded from public reads). Like `BoardSort`, it's URL-driven: it writes `?status=` (omitted for "all") and the Server Component (`app/portal/[tenant]/page.tsx`) re-renders with `filters.status` passed to `publicApi.getBoard`. The tabs render even when the filtered list is empty (so the visitor can switch back); the empty card reads `portal.noMatchingPosts` under a filter, `portal.noFeedbackYet` on "all". Status values are validated by `normalizeBoardStatus` (`lib/api/public.ts`, `PUBLIC_BOARD_STATUSES`).
- Visitors **can submit feedback** (`components/portal/feedback-submit.tsx`, POSTs to `/public/:tenant/feedback`) and **upvote** (`components/portal/portal-vote-button.tsx`, toggles `/public/:tenant/posts/:id/vote`). A submission **requires a contact email** (name stays optional) so the team can reach the submitter about their post — enforced on the client and again in `createPublicPost` (`400 email_required` when `author_id` is null and no email). **This applies to *every* submitter, signed in or not**: `feedback-submit.tsx` never sends a Bearer token, so `author_id` is always NULL and a post is identified by the typed name/email, not by an account. (The backend route *is* `optionalAuth` and would attribute a post if a token were sent — it just isn't. Don't document account attribution for posts until the form actually sends one; the docs claimed it for a while and the code never did.) The email is never exposed in public reads. Anonymous identity for vote spam-control comes from `lib/portal/guest.ts` — a persistent `fb_guest_id` cookie (sent to the backend) plus a localStorage hint for the filled state. The tenant logo (`components/portal/portal-logo.tsx`) falls back to a brand-colored initial if missing/broken.
- **Guest display identity.** A guest who leaves no name isn't shown as a flat "Anonymous". `lib/portal/anon-identity.ts` (`guestIdentity` / `colorFor`) deterministically derives a friendly pseudonym (e.g. "Brave Otter") + an avatar colour from the guest's `fb_guest_id`, so one guest is **consistent** across their posts/comments and **distinct** from other guests. The `fb_guest_id` is now stored on the post/comment (`posts.guest_id` / `comments.guest_id`, sent by `feedback-submit` and `portalActions.createComment`, returned by the public read endpoints) so the identity is stable server-side too; older rows without it fall back to a per-item key. Guests who *do* leave a name keep it (just coloured); logged-in authors always show their real name + avatar. Purely presentational — no PII is derived or exposed.
- **Logged-in users on the portal.** `PortalComments` and `PostOwnerActions` read `useSession()`; when logged in, a comment/post is sent with the Bearer token (backend attributes it to the user, showing their name + avatar) and the author can **edit/delete their own** post/comment via `lib/portal/actions.ts` (`portalActions`). Ownership is compared client-side (`comment.author_id === session.user.id`) for showing controls and **enforced server-side**. The session must reach the portal host, so in **production** the auth cookie is scoped to the parent domain (`auth.ts` `SESSION_COOKIE_DOMAIN` = `.<root domain>`) and every `*.<root domain>` subdomain shares the login. Changing that cookie domain invalidates existing sessions, so re-login after deploying it. The cookie is only scoped to a **real, dotted** root domain — browsers/RFC 6265 never set a `Domain` cookie for a single-label host like `localhost` or a bare IP (verified against curl), so those stay host-only. **Consequence in dev:** with `NEXT_PUBLIC_ROOT_DOMAIN=localhost:3000` the cookie is host-only and a logged-in session **cannot** reach a `*.localhost` subdomain. Two ways to test logged-in portal actions locally: **(1)** the direct path `http://localhost:3000/portal/<tenant>` (same origin as login → cookie present); or **(2)** set `NEXT_PUBLIC_ROOT_DOMAIN=lvh.me:3000` (wildcard `*.lvh.me` resolves to 127.0.0.1), log in at `http://lvh.me:3000`, and open `http://<tenant>.lvh.me:3000` — the `.lvh.me` cookie is shared across subdomains exactly like production. `SESSION_COOKIE_DOMAIN` is computed from the domain *shape* (dotted-and-not-IP → `.<root>`, else host-only), so it's correct in every environment with no `NODE_ENV` branch.
- **Verified-admin badge.** A comment/post whose author account is a **platform admin** shows a rose `BadgeCheck` **verified tick** beside the name (`components/portal/verified-badge.tsx`), so visitors can tell an official reply from FeedBoard's team apart from an ordinary user. The flag is `author_is_admin`, added to the public reads (`getPublicPostDetail`) **and** the authenticated dashboard comment read (`getPostComments`) as `EXISTS(SELECT 1 FROM admins a WHERE a.email = u.email AND a.is_active = 1)` — driven by the `admins` table, never a name or the tenant's own `owner` role. Rendered in `PortalComments` (`CommentCard`), on the post-detail author line, and in the dashboard `CommentThread`. Purely presentational; the email itself is never exposed.
- **Replying to feedback from the dashboard.** The dashboard feedback detail's `CommentThread` (`components/feedback/comment-thread.tsx`) is **no longer read-only** — a signed-in team member can post a comment or a threaded reply via `commentsApi.create` (attributed to their account). This is the **reliable, same-origin** way for the platform admin (in the board's user session via *Open in dashboard*) to reply and have it show as a **verified admin**: an admin token isn't accepted by the portal's `optionalAuth` (no `sid`), and in dev the portal subdomain can't see the localhost login cookie — so a reply typed on the public portal while "logged in as admin" would be stored as an anonymous **guest**. Replying from the dashboard sidesteps both. (Editing feedback text is still not offered — that belongs to its author.)
- **Sharing & rich previews.** The post page (`app/portal/[tenant]/post/[id]`) has `SharePost` (`components/portal/share-post.tsx`) — copy link, native `navigator.share`, and social intents — and a `generateMetadata` that emits Open Graph + Twitter Card tags. `SharePost` takes an optional `url` (defaults to the current page) so the **dashboard** feedback detail reuses it: it resolves the tenant (`tenantsApi.getMine`), builds the public URL (`<subdomain>.<root>`), and shows a **Share** action. (The team does not edit the feedback text — it belongs to its author — but can Share, Pin, set status, owner/Pro-gated Delete, and **reply in the comment thread**.) `opengraph-image.tsx` in the same segment renders a **dynamic branded preview image** (`next/og` `ImageResponse`, 1200×630) per post. `metadataBase` is derived from the request `host` header so OG URLs are correct on the tenant's subdomain. `publicApi.getPost` is wrapped in React `cache()` so metadata + page + OG image share one backend call.
- **Timestamps.** `components/local-time.tsx` (`LocalTime`) renders timestamps in the **viewer's** locale/timezone — `relative` gives a live "time ago" label (via `Intl.RelativeTimeFormat`, refreshed each minute, absolute date/time on hover), else an absolute localized date/time (`Intl.DateTimeFormat`). Formatting lives in `lib/time.ts`. It's client-only (with `suppressHydrationWarning`) so it localizes per viewer. Used on board cards, comments/replies, and the post detail.
- Local testing: visit `http://<tenant>.localhost:3000` (Chrome resolves `*.localhost`) or `/portal/<tenant>` directly. **For *logged-in* portal actions, use `http://localhost:3000/portal/<tenant>`, or switch to a dotted loopback domain (`NEXT_PUBLIC_ROOT_DOMAIN=lvh.me:3000` → `http://<tenant>.lvh.me:3000`)** — a `*.localhost` subdomain can't receive the login cookie in dev (see the logged-in-users note above).

### FeedBoard's own feedback board (dogfooding)

- FeedBoard collects feedback about **itself** on an ordinary tenant portal — **not** a special-cased surface. A workspace with subdomain `NEXT_PUBLIC_FEEDBACK_SUBDOMAIN` (default `feedback`) is owned by the **platform admin's own `users` account** (platform admin is a role on that account — `users.is_platform_admin`), created by the backend's `scripts/create-official-board.js` (idempotent, picks the flagged account). The admin signs in normally and finds it in the workspace switcher, and can also moderate it at `/admin/workspaces/<id>`. It's comped to **Business** so the board itself has every capability.
- **Brand icon as admin identity.** FeedBoard's app icon (`app/icon.svg`, the rose **"F" monogram** — three board rows forming the letter, white on the rose→secondary gradient) is the platform's visual mark. The backend keeps a copy at `assets/app-icon.svg` and serves it from `uploads/branding/app-icon.svg` (`src/common/brand-asset.js` `ensureBrandAsset()`); `scripts/set-official-branding.js` (idempotent) — and `create-official-board.js` on setup — set it as **the platform admin's profile picture** (`users.avatar_url` on every row for the admin's email) and **the official board's logo** (`tenants.branding_logo_url`). So the admin's avatar in the dashboard header, the official board's `PortalLogo`, and the admin's comment avatar (via `author_avatar`) are all the app icon. Re-run `set-official-branding.js` after adding admin memberships.
- **The mark lives in FOUR places and they must not drift**: `app/icon.svg` (favicon), `components/ui/logo.tsx` (the inline React `Logo`), `public/logo.svg` + `logo-120.png`/`logo-512.png` (external consumers — Google's OAuth consent screen rejects SVG, hence the PNGs, which are rendered from the SVG rather than drawn separately), and the backend's `assets/app-icon.svg`. **Changing `assets/app-icon.svg` is not enough on its own**: `ensureBrandAsset()` runs only from those two scripts, never at boot, and `uploads/` is a persistent volume — so after a logo change you must re-run `node scripts/set-official-branding.js` on the server or the admin avatar and official board keep serving the old icon.
- **`lib/official-board.ts`** is the single source of the link. `officialBoardUrl()` returns `https://<sub>.<root>` in production, but the direct `/portal/<sub>` path on a single-label host (`localhost`, a bare IP) — a `*.localhost` subdomain can't receive the auth cookie in dev, so the direct path is the only form that keeps a signed-in developer signed in.
- **Access points**: the dashboard sidebar has a single **"Public board"** link (the current workspace's portal — for the official board that IS the feedback board); the separate "Give feedback" dogfood link was removed. Signed-out visitors reach the official board from the landing-page footer. Both audiences are handled by the portal itself — a guest posts anonymously (contact email required), a signed-in user is attributed to their account and can edit their own posts.
- **Comment identity choice (plan-gated).** A privileged commenter picks the identity via a **"Comment as" selector** (`CommentAs = "self" | "owner_named" | "owner_hidden" | "anonymous"`), applied to the comment and its replies. Which options appear is gated by the **board's plan** (two limits in `src/consts/plans.js`: **`ownerBadge`** = Pro+, **`ownerPrivacy`** = Business), surfaced to the portal via `publicApi.getTenant()` booleans **`owner_badge_enabled` / `owner_privacy_enabled`** and to the dashboard via `billingApi.getStatus().limits`.
  - **self** → attributed to them; a **platform admin** shows the verified-admin tick. Note: an owner who has the named badge does **not** get a redundant plain-name option — "Name (Owner)" replaces "self" for them (the option list is computed in `identityOptions`, coerced via `commentAsEff`); "self" remains for non-owner admins/members.
  - **owner_named** (Pro+, board OWNER) → shows **"Name (Owner)" + verified-owner tick**, real name kept.
  - **owner_hidden** (Business, OWNER) → shows **"Owner" + tick**, real name/avatar **withheld server-side**.
  - **anonymous** → posted **without the token** (guest, no `author_id`/tick), so a logged-in user can comment without their identity. Offered to **every logged-in user** (a regular member gets **self / anonymous**) — the one exception is a **Free board owner**, who is blocked from commenting on their own board (a Pro feature); a platform admin always keeps it. Gated by `canAnonymize = isLoggedIn && (isPlatformAdmin || !ownsBoard || ownerBadge)`.
- **Posting and commenting are FREE on every plan — including the board's own owner. What a paid plan buys is the IDENTITY, never the right to speak.** This was the other way round once (`402 owner_post_pro` / `402 owner_comment_pro` blocked a Free owner outright); both gates are gone, along with the PRO-prompt composers and the `ownerBlocked` / `canReply` plumbing. The rule now has one shape: **`self` (plain name) is always available**, and `ownerBadge` (Pro+) / `ownerPrivacy` (Business) only add *extra* identities on top. Consequences worth keeping straight:
  - **What a plan actually sells is the verified TICK**, i.e. the two badged identities: `owner_named` ("Name (Owner)" + tick, Pro+) and `owner_hidden` ("Owner" + tick, real name withheld, Business). Nothing else about commenting is gated.
  - `identityOptions`: a Free owner gets **`self` + `anonymous`**; a Pro owner gets **`owner_named` instead of `self`** (the badge replaces the plain name, so there's no redundant duplicate) + `anonymous`; Business adds `owner_hidden`. Any other logged-in user gets `self` + `anonymous`.
  - **`anonymous` is free for everyone, the board owner included** (`canAnonymize = isLoggedIn`). It *withholds* an identity rather than granting one, which is the opposite of what a plan sells — so gating it never made sense. It works by simply **not sending the Bearer token**, so the comment is stored as an ordinary guest: there is no server-side gate to enforce, and none exists.
  - Server-side, an unentitled `ownerMode` now **falls back to `as_owner = 0`** rather than rejecting — nobody loses what they typed to a paywall. `resolveOwner` (`createPublicComment`) returns `{ asOwner }` only; there is no `blocked` flag left.
  - The Pro bullet is `plan.feat.commentAsOwner` = *"Reply with a verified Owner badge"* — it names the badge, so it can't be misread as permission to reply at all.
  - **Public post submission is unaffected by identity work because it has none**: `feedback-submit.tsx` always posts as a **guest** (no Bearer token, email always required), even for a signed-in visitor. Attribution and the owner badge live on **comments** only.
  - **Comment avatar follows the identity.** On the public board (`commentDisplay` in `PortalComments`): a **platform admin** shows the **app icon** (their persisted `author_avatar`); **owner_named** (mode 1) shows the owner's **profile picture**; **owner_hidden** (mode 2) shows the **workspace's own logo (company icon)** — `getPublicPostDetail` returns `bt.branding_logo_url` as `author_avatar` for mode 2 (real name still withheld → "Owner"). Falls back to the coloured initial when a logo/avatar is missing.
  - Stored in **`comments.as_owner`** (0 none / 1 named / 2 hidden). The create handlers (`createPublicComment`, `createComment`) **re-gate by plan** via `getTenantPlan` + `getPlanLimits` — the client selector is UX only. The reads (`getPublicPostDetail`, `getPostComments`) return `author_as_owner` (validated the author owns the board) and hide the name **only for mode 2** (whose avatar becomes the company logo). The **dashboard** `CommentThread` offers self / owner_named / owner_hidden (no anonymous — authenticated `/comments/create`). Requires being logged in **on the portal**, so "Public board" links use `portalUrlForSubdomain` to carry the session in dev.
- **Admin shortcut**: because the platform-admin session can't reach the tenant dashboard (it's redirected to `/admin`), `components/admin/admin-sidebar.tsx` shows an **"Our feedback board"** link that deep-links to the board's admin moderation page (`/admin/workspaces/<id>`). The tenant id is resolved at runtime via `adminApi.listWorkspaces(token, officialBoardSubdomain)` (never hardcoded) so it tracks `NEXT_PUBLIC_FEEDBACK_SUBDOMAIN`; the item is hidden if the board doesn't exist.
- **"Open in dashboard" (admin → user handoff)**: the admin moderation page (`app/admin/workspaces/[id]`) shows an **Open in dashboard** button **only when the admin has their own active member account in that workspace** (detected client-side from the `members` list; the button gives the full dashboard the moderation page can't — roadmap, changelog, replies, notify-submitter). It calls **`adminApi.enterWorkspace(token, id)`** → `POST /admin/workspaces/:id/enter`, which mints a tenant-scoped **user** token for the admin's own account there (`403 admin_not_member` otherwise; server-enforced, so the client gate is just UX). The client then `update()`s the NextAuth session from admin → that user identity — **the `jwt` "update" handler flips `isAdmin`/`adminId`/`email`** so the dashboard stops bouncing it to `/admin` — and hard-navigates to `/dashboard/feedback` (soft refresh races the cookie write, same as the workspace switcher).
- **The handoff is REVERSIBLE — no re-login.** A browser holds one NextAuth session (one identity), so the admin can't be admin-and-user simultaneously; instead the entry stashes a **`savedAdmin` snapshot** (admin token + identity) on the session (`types/next-auth.d.ts` `SavedAdminIdentity`; carried through the `jwt` "update" handler). While that snapshot is present, `components/dashboard/admin-return-banner.tsx` (mounted in the dashboard layout) shows a **"Back to admin panel"** bar that `update()`s the admin identity back (restores the admin token, `isAdmin:true`, clears `tenantId`/`savedAdmin`) and returns to `/admin` — instant, password-free. So the admin round-trips admin ⇄ board dashboard freely. (Direct navigation to `/admin` while in board mode still bounces to `/admin-login` since `isAdmin` is false there — use the banner button.)

### Legal pages

- Four public documents at **`app/legal/{terms,privacy,cookies,refunds}`**, sharing `components/legal/legal-shell.tsx` (chrome, doc switcher, `Clause`/`Bullets`/`LegalTable` primitives). Linked from the landing footer, the **portal** footer (visitors are on our infrastructure, so the links must be reachable from a tenant board — via `appUrl` since the portal runs on a subdomain) and the signup form.
- **Deliberately NOT localized.** Machine translation is fine for UI labels but a mistranslated liability or refund clause is a real liability, so each page states English as the authoritative version. Don't wire these into `common.json`.
- **`lib/legal.ts` is the single source** of entity name, address, jurisdiction, contact emails and the last-updated date. A blank `entity`, `jurisdiction` or `courts` renders as a highlighted `[ADD: …]` marker via the `Fill` component, so an unfilled document can't ship unnoticed. Bump `lastUpdated` whenever the text changes.
- **`address` is deliberately blank, and blank is a valid state there — not a missing `Fill`.** FeedBoard is a sole proprietorship run from a residential address, and publishing a home address is a personal-safety problem rather than a compliance win. The Terms and Privacy pages therefore identify the operator by **trading name + jurisdiction** and render *"postal address available on request"* pointing at `contactEmail` — which is a real obligation, so **the address must actually be given when someone asks**. This holds up because **Paddle is merchant of record**: the payment contract is with Paddle, who publishes their own trader details at checkout and holds verified identity for the business. Both pages say so explicitly. **If you ever switch to `BILLING_PROVIDER=stripe` you become the trader yourself**, and EU consumer law wants a real geographic address again — set `address` (a registered business or virtual-office address, never a home one) and the pages print it in place of the on-request wording.
- **There is no refund window: paid periods are non-refundable.** Cancelling sets Stripe's `cancel_at_period_end`, so access continues to `currentPeriodEnd` and no proportion is returned — the Refund Policy documents exactly that mechanism. Two deliberate exceptions, both narrow: **billing corrections** (duplicate charge, charge after cancellation took effect, wrong plan/interval charged — an error, not a refund) and the **Terms §10 remedy** if we materially reduce a paid plan mid-term. Don't add a goodwill window to the page without also deciding who honours it.
- The content describes **actual behaviour** — the 8-hour domain-scoped session cookie, the one-device limit on Free/Pro, `fb_guest_id`, guest submitter emails never being shown publicly, bcrypt hashes, Stripe-hosted checkout, proration on upgrade vs scheduled downgrade, and what account deletion does to owned vs joined workspaces. If any of that changes, the affected policy is part of the same change.

### Internationalization (i18n)

- **Stack**: `i18next` + `react-i18next`, **cookie-based** (no `[lng]` URL segment — that would fight the subdomain proxy). Config in `lib/i18n/`: `settings.ts` (the **8 major EU languages** — English, German, French, Spanish, Italian, Portuguese, Dutch, Polish — English default/fallback, `cookieName = "i18next"`, native-name `languageOptions`), `client.ts` (browser singleton — **deliberately no `LanguageDetector`**), `server.ts` (`getLanguage()` reads the cookie via `next/headers`; `getTranslation(lng?, ns?)` for Server Components). `components/providers/i18n-provider.tsx` wraps the app in the root layout (seeded with the server-resolved language; sets `<html lang>`).
- **The server-resolved language is the single source of truth.** `getLanguage()` reads the `i18next` cookie (no cookie ⇒ English; `navigator` is intentionally ignored) and the root layout passes it to `I18nProvider`, which both drives `i18next.changeLanguage` and exposes it via a `useLanguage()` context. **Client components must read the active language from `useLanguage()`, never from `i18n.resolvedLanguage`** — the latter settles asynchronously as the locale bundle loads and can report the fallback instead, which is what made the navbar selector show "English" on a Polish page. For the same reason the selector renders its label as explicit `<SelectValue>` children: Radix resolves an item's label only on the client, so otherwise the trigger server-renders blank.
- **English is the source of truth**; every other language falls back **per-key** (`fallbackLng: "en"`), so a partial translation never shows a broken key. Dictionaries live in `lib/i18n/locales/<lng>/common.json` (namespace `common`). `en/common.json` is complete; the other 7 hold the translated subset and fall back for the rest. Translations are **machine-generated — review before production.**
- **Language selector** (`components/i18n/language-selector.tsx`) is in every navbar (landing, dashboard header, admin header) **and in the public portal header** — portal visitors are the tenant's own users and never see the dashboard navbar, so they get their own control. It takes an optional `iconColor` (the portal passes the tenant's brand colour so the globe doesn't clash with their branding). Changing it writes the `i18next` cookie, calls `i18next.changeLanguage`, and `router.refresh()`es so Server Components re-render in the new language.
- **Usage**: Server Components — `const { t } = await getTranslation()` then `t("nav.pricing")`. Client Components — `import { useTranslation } from "@/lib/i18n/client"` then `const { t } = useTranslation()`. The **landing page (`app/page.tsx`) is fully localized** as the reference pattern; other surfaces (auth, dashboard, admin, portal) follow the same approach — add keys to `en/common.json` and translate.
- **Backend language**: `lib/api/client.ts` sends `lg` = the active UI language (read from the `i18next` cookie via `currentLanguage()`), so backend responses are localized too. English on the server / before a choice.
- **Stored text can't be translated on read.** A notification's `title`/`message` are written **once, in English**, when the event happens — a reader in another language would still see English. So `notifications.meta` (JSON) carries the **structured pieces** (`{ key: "comment", postTitle, who, body }`, written by `notifyTeam`) and the client renders them through `t()` in the *reader's* language (`notif.commentTitle` / `notif.commentMessage`). `title`/`message` remain the English fallback for rows written before the column existed. **Any new notification type must add its `meta` shape + i18n keys**, or it will be stuck in English. The same rule applies to anything else persisted as prose.
- **Never format dates/times with the browser locale.** `Intl.*` with no locale uses the *browser's*, which drifts from the chosen UI language (a German page showing "3 days ago"). Always render timestamps via `components/local-time.tsx` (`LocalTime`), which takes the language from `useLanguage()`.
- **Plurals**: Polish has `one/few/many` categories that English lacks. A key with only `_one`/`_other` silently falls back to **English** for counts of 2+ in Polish — add `_few` and `_many` for every plural key.

### Authentication & session

- NextAuth v5 (beta), **Credentials + Google**; config in `auth.ts`. The JWT stores `userId`, `accessToken`, `tenantId`, `role`, and (for admins) `isAdmin` + `adminId`. Session type augmentation is in `types/next-auth.d.ts`.
- **"Continue with Google" (`components/auth/google-button.tsx`, on both login and signup).** NextAuth owns the handshake; the **`signIn` callback then trades the verified identity for a FeedBoard session** via `loginWithOAuth` → `POST /users/oauth/login`, and `Object.assign`s the result onto `user` so the `jwt` callback picks it up on the same pass. The backend stays the single source of truth for accounts, plans and the device limit. Scopes are **`openid email profile` only** — the non-sensitive set, which is what keeps Google's review on the light path and avoids the paid security assessment that restricted scopes require. Env: `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` (NextAuth reads those names automatically); redirect URI is `<origin>/api/auth/callback/google`.
  - **`emailVerified` is mandatory, and it's a security boundary, not a formality.** The backend matches an existing account **by email**, so accepting an unverified provider address would let anyone who can put an arbitrary email on a provider profile claim someone else's FeedBoard account. Checked in the `signIn` callback *and* again in `oauthLogin` (`400 oauth_email_unverified`). Any future provider that doesn't report verification must not be enabled without another check.
  - **A social signup gets NO workspace** (`tenant_id` NULL) and no password, exactly like an email signup, then lands on `/onboarding`. The old `oauthLogin` defaulted to **`tenantId: 1`** — that would have dropped every new social signup into whichever workspace is first (a real customer's board). Never reintroduce a tenant fallback.
  - **`oauth_accounts` is account-keyed**: `(email, provider, provider_user_id)`, `UNIQUE (provider, provider_user_id)`, **no FK to `users`** — the link is created when the account has no workspace and must outlive any membership row (same shape as `user_sessions` / `password_resets`). The provider's **subject id** is the identity, so changing the address on the Google account still signs in to the same FeedBoard account. `purgeAccount` deletes it by email; nothing cascades it. Migrate with `scripts/rebuild-oauth-accounts.js` (refuses to touch a non-empty old-shape table).
  - **OAuth failures redirect** rather than returning a result, so they come back as `?oauth_error=` on `/login` (`lib/auth/oauth.ts`). The **device-limit 409 still offers the takeover**: `GoogleButton force` writes a one-shot `fb_oauth_force` cookie that the `signIn` callback reads and deletes — a redirect flow has no request body to carry `force` in, unlike password login.
- **Password-less accounts are a first-class state now.** A Google account has `password_hash NULL`, which two flows have to respect: **account deletion** skips the password re-check when there is none (`getAccountDeletionSummary` returns `hasPassword`, and the dialog hides the field — otherwise the account would be undeletable), and **"Forgot password" deliberately no longer requires `password_hash IS NOT NULL`**, so it doubles as *set* a password. Without that, "Continue with Google" would be a one-way door: lose the Google account, lose the workspace.
- **Three roles total.** Tenant roles are **`owner`** (manages the workspace — all admin-only settings tabs, billing, feedback deletion) and **`user`** (member; Profile tab only). The **platform `admin`** is a *separate identity*, not a tenant role — see below.
- **Platform admin & Admin Panel.** "Platform admin" is a **role flag on the operator's `users` account** (`users.is_platform_admin`) — there is no separate `admins` table. The **same account** is a normal tenant user via `/login` and an admin via `/admin-login`; the login door decides which session you get. The Credentials provider takes an `accountType` field: `accountType:"admin"` authenticates via `loginAsAdmin` (`lib/auth/auth-service.ts` → backend `POST /admin/auth/login`, which now checks the `users` password **and** the admin flag) and sets `isAdmin:true`, `adminId` (a `users.id`), an admin `accessToken`, `tenantId:null`, `role:null`. Sign in at **`app/admin-login`** (a standalone, admin-styled page outside the customer `(auth)` layout); the dashboard layout redirects an `isAdmin` session to `/admin`. The gated panel (`app/admin/`, `layout.tsx` redirects non-admins to `/admin-login`) uses **`lib/api/admin.ts` (`adminApi`)** — a REST client sending the admin token to backend `/admin/*` — to manage all workspaces (incl. plan grant/comp, and **moderate their posts** — status/pin/delete, plus each post's **comments** (view/delete via a dialog — no editing) — at `app/admin/workspaces/[id]`), all users (role/reset/deactivate/delete), other admins, promo codes, **offers** (promotional plan prices), and view platform stats.
- **Support chat (user ↔ platform admin).** Every dashboard user (any role, any plan — **not** gated) gets a floating **Contact support** widget (`components/support/support-chat-widget.tsx`, mounted in `app/dashboard/layout.tsx` next to `SingleTabGuard`/`Toaster`). It opens a **session** with the platform admin via `supportApi` (`lib/api/support.ts` → `/support/*`, Bearer-authed): `openSession` (get-or-create — a user has **at most one open session**), `listMessages`, `sendMessage`, `unread`. **A session is created lazily — only on the user's first message**, so opening the widget and leaving never spawns an empty conversation; the widget resumes an existing open session via `unread` (which returns its id) and calls `openSession` at first-send. As a backstop, the admin queue **hides message-less sessions** (`listSessions` requires `EXISTS` a message). The admin side is `app/admin/support/page.tsx` (Open/Closed queue + transcript + reply + **Close chat**) using `adminApi.listSupportSessions/getSupportSession/sendSupportMessage/closeSupportSession/supportInboxUnread`; the admin sidebar shows an unread badge (count of open sessions with waiting user messages). **Real-time is polling** (no WebSocket infra): open panels poll messages every ~4s, badges every ~15–20s. A **notification bell** rings when a new *incoming* message arrives while the page is open — the user hears an admin reply, the admin hears a user message. It's a Web-Audio chime synthesized in `lib/notification-sound.ts` (`playNotificationBell`, throttled; `armNotificationSound` resumes the AudioContext on first gesture per the autoplay policy) — no audio asset. Each poller rings only on an *increase* past a primed baseline (never on first load or your own messages). **On close, the user loses access** — every user read is scoped to `status='open'`, so a closed session 403s and the widget shows "closed → Start new chat" (which creates a fresh session); the **admin keeps the full transcript forever** (sessions are never deleted, `user_id`/`tenant_id` go `SET NULL` on account/workspace deletion and the display identity is denormalized on the session row). Lint note: put each polling effect's async work in a **nested function** inside the effect (see the widget/admin page) — the React Compiler's `set-state-in-effect` rule rejects a `setState`-bearing call made directly in the effect body.
- **Exactly one `SessionProvider`.** It lives in the root `app/layout.tsx` (`AuthSessionProvider`), seeded with the server session. **Do NOT add a second/nested `SessionProvider`** (e.g. in the dashboard layout) — nesting breaks `useSession().update()`, so client-side session refreshes silently fail (this caused the header avatar not to update after a profile edit).
- Profile edits call `update({ name, image })` to refresh the session in place; `auth.ts`'s `jwt` callback handles the `"update"` trigger. The header reads name/avatar from the live session so it re-renders immediately.
- **Multiple workspaces per account.** An email can be a user in several tenants. `components/dashboard/workspace-switcher.tsx` (sidebar) lists `usersApi.getWorkspaces()`, and switching/creating calls `usersApi.switchWorkspace()` / `createWorkspace()` then `update({ accessToken, tenantId, role, userId })` — the `jwt` "update" handler swaps the active identity. **After `await update(...)` do a hard reload (`window.location.assign("/dashboard")`), not `router.refresh()`** — a soft refresh races the session-cookie write, so the switch wouldn't take effect until a second click. The create forms (onboarding + switcher dialog) check subdomain uniqueness live via `usersApi.checkSubdomain` + `useSubdomainAvailability` (debounced) and disable Create unless it's available; the backend also enforces it (pre-insert check + `UNIQUE` constraint + `ER_DUP_ENTRY` fallback). `resolveUploadUrl` (`lib/avatar.ts`, aliased as `resolveAvatarUrl`) turns a backend-relative upload path into a loadable API-origin URL — used for avatars **and** the tenant logo (uploaded via `uploaderApi.uploadImage` in Branding settings and shown by `PortalLogo` on the public board; the portal layout resolves it before rendering).
- **Onboarding.** A new signup has **no workspace** (`session.user.tenantId` is null). The dashboard layout redirects such users to `app/onboarding/page.tsx` (and signup redirects there directly) to create their first workspace; creating it claims their account row and re-scopes the session. They never see other tenants' data.
- **Delete account.** `components/settings/delete-account.tsx` (a Danger-zone card at the bottom of Settings → Profile). The dialog first loads `usersApi.getDeletionSummary()` and spells out exactly what dies: **workspaces you own are deleted** (with their posts/roadmap/changelog, all members lose access, subscription cancelled) while **shared workspaces survive** (your posts/comments there stay but become anonymous). Deleting requires the **password** plus typing `DELETE`, then signs out. Owned workspaces are destroyed because a workspace has exactly one owner and there is no ownership transfer.
- **Deleting an account is ONE cascade — `src/common/accountDeletion.js` (`purgeAccount`) — shared by the customer flow and the Admin Panel**, so the two can't drift. An account is an **email** with one `users` row per workspace, so a delete is never a single `DELETE FROM users`: that either fails outright (`posts.author_id`, `changelog_entries.created_by`, `api_keys.created_by`, `file_uploads.uploaded_by` are **ON DELETE RESTRICT**) or strands the workspace, the `billing_accounts` row, device sessions — **and a live subscription that keeps charging a customer who no longer exists**. That's how workspace `fire-world` ended up with no owner. The purge, in order: **cancel the subscription on the active provider** (via `cancelActiveSubscription`, so it's Paddle *or* Stripe — done **outside the transaction**, because a real charge must not be undone by a rollback), delete **owned** tenants, **anonymise** (`author_id → NULL`) and **reassign** RESTRICT rows to the owner in **joined** ones, then clear `users` / `billing_accounts` / `user_sessions` / `password_resets` / `invitations` for the email. **`promo_redemptions` is deliberately kept** — it's the ledger behind "one redemption per account", and clearing it would let someone delete their account to re-redeem a code. `support_sessions`/`support_messages` are `SET NULL`, so the admin keeps the transcript.
- **A platform admin can't be deleted as a user.** `/admin-login` and `authenticateAdmin` both authenticate against `email = ? AND is_platform_admin = 1`, so removing that row locks **every** admin out with no way back in. `purgeAccount` refuses with `platform_admin_undeletable`; revoke the role under **Admins** first. The flag is meant to be account-wide (`manageAdmins` sets it `WHERE email = ?`) but rows created later start at 0 — `scripts/cleanup-orphans.js` backfills that drift (and reports/removes ownerless workspaces) so the role never hangs off a single deletable row.
- **Admin Panel → Users is account-scoped where it matters.** A row is one membership, so **role** and **active** are per-row, but **password reset** writes the hash to every row for the email (an account has one password — matching `passwordReset.js`) and revokes its sessions, and **delete** purges the whole account. The delete dialog loads `adminApi.getUserDeletionSummary` first and lists the workspaces that will be destroyed, the ones that survive, and whether a live subscription gets cancelled — a destructive action is never taken blind. A row with **no workspace** is a legitimate state (signed up, not yet onboarded — and the platform-admin identity lives on exactly such a row); it renders as "No workspace", not as a broken empty user.
- **Forgot / reset password.** The login page (`components/auth/login-form.tsx`) has a **"Forgot password?"** link → `app/(auth)/forgot-password/page.tsx`. Submitting an email posts to `app/api/auth/forgot-password/route.ts` (IP rate-limited, mirrors the register route) → backend `POST /users/password/forgot`, which **always** returns the same neutral success (no account enumeration) and, when the email matches an active account, emails a **1-hour, single-use** link to `/reset-password/<token>`. `app/(auth)/reset-password/[token]/page.tsx` (Server Component) validates the token via `publicApi.validateResetToken` (→ `GET /users/password/reset/:token`, returns a **masked** email) and renders either an invalid/expired state (with a "request a new link" link) or `components/auth/reset-password-form.tsx`. Submitting posts to `app/api/auth/reset-password/route.ts` → `POST /users/password/reset`; on success it redirects to `/login?reset=success` (the login form shows a success banner in the same slot as the `reason=session_ended` one). The backend (`src/main/users/passwordReset.js`) stores only a **sha256 hash** of the token, updates **all `users` rows for the email** (an account's workspaces share one `password_hash`), and **revokes every device session** for the account. New service fns: `requestPasswordReset` / `submitPasswordReset` (`lib/auth/auth-service.ts`); schemas `forgotPasswordSchema` / `resetPasswordSchema` / `resetPayloadSchema` (`lib/auth/schemas.ts`).
- **Team invitations.** The **owner** invites teammates by email from Settings → Team (`invitationsApi`); the backend emails a single-use, 7-day link to `/invite/<token>`. `app/invite/[token]/page.tsx` (Server Component) resolves the token via `publicApi.getInvitation` and renders `components/invite/invite-accept.tsx`: an **existing** account must be signed in as the invited email and joins in one click; a **new** person sets a name + password, is signed in, and is sent to `/onboarding?invited=<tenantId>` — they create their **own** workspace and are then switched into the workspace that invited them. Over the plan's seat limit the invite returns `402` and the UI toasts an **Upgrade** action. The limit counts team members **besides the owner** (`limits.seats`): Free = owner + 2, Pro = owner + 5, Business = unlimited.
- **Two kinds of workspace.** A workspace has exactly **one owner**; everyone else is a member. `usersApi.getWorkspaces()` returns `role`, so `WorkspaceSwitcher` groups the sidebar dropdown into **"Your workspaces"** (owned) and **"Shared with you"** (joined by invite), and tags the active one with a **Member** chip when it isn't owned. The Team tab therefore shows roles as read-only badges — there is no valid role change under the one-owner rule.
- **Per-account workspace limits.** How many workspaces an account may **own** and **join** is capped by the account's tier (its subscription plan, per-account): Free owns 1 / joins 1, Pro 3 / 3, Business unlimited. `usersApi.getWorkspaces()` now returns a `limits` object (`WorkspaceLimits`: `canCreate` / `canJoin` / counts / `ownLimit` / `joinLimit`, limits `null` = unlimited). `WorkspaceSwitcher` reads it: at the owned cap it replaces **Add Workspace** with a locked "upgrade to add more" item routing to `settings?tab=billing`, and a `402` on create still toasts an **Upgrade** action. Enforced server-side (`402 plan_limit_workspaces_own` on create, `402 plan_limit_workspaces_join` on invite accept). The invite-accept page surfaces the join-limit message directly. To lift the cap, upgrade your **account** (any owned workspace's Billing tab) to Pro/Business.
- **One device at a time (Free/Pro) — device sessions.** Every user JWT carries an `sid` claim naming a row in the backend's `user_sessions` table, keyed by **email** (so switching workspaces re-uses the same session and is *not* a new device). On plans without the `multiDevice` limit (Free, Pro) a **second login is refused with `409`**; Business allows unlimited devices. Three consequences for this codebase:
  - **Surfacing the error.** A Credentials provider normally collapses every failure into one opaque error. `auth.ts` throws an `ActiveSessionError extends CredentialsSignin` with `code = "active_session"` (from `lib/auth/signin-errors.ts`) when the backend answers `409`, and NextAuth hands it back as `signIn(...).code` — that's how `login-form.tsx` shows "already signed in on another device" instead of "invalid password".
  - **Takeover escape hatch.** A `409` means the password was *correct*, so the account owner isn't locked out: `login-form.tsx` shows a **"This is me — sign out other devices and sign in here"** button that re-submits `signIn` with `force: "true"`. `auth.ts` passes it through as a `force` credential → `loginWithCredentials({ force })` → `POST /users/login` with `userData.force`, which revokes the other sessions and logs in. Without this, a stale session (browser closed without signing out) would block the owner for up to the 15-min idle window.
  - **Signing out must revoke the session.** Use **`endSession(accessToken)`** (`lib/auth/end-session.ts`) — never bare `signOut()`. Dropping the cookie alone leaves the server-side session alive, and the user is then told they're "already signed in elsewhere" when they try to come back. (Best-effort: if the revoke call fails we still sign out locally.)
  - **A revoked token 401s.** `lib/api/client.ts` turns any `401` into a one-shot sign-out to `/login?reason=session_ended` (the login form explains it), so a taken-over device doesn't sit in a dashboard where every request fails.
  - **Abandoned sessions** (browser closed without signing out) are taken over by the next login once idle >15 min — otherwise the user would be locked out for good. The takeover revokes the old session, so at most one is ever live.
- **Second *tab*** is a client-only problem: it reuses the session cookie, so there's no login event for the server to refuse. `components/dashboard/single-tab-guard.tsx` (mounted in the dashboard layout, `multiDevice` read server-side from `billingApi.getStatus()`, **failing open**) does a `BroadcastChannel` claim/taken/released handshake between tabs and blocks the duplicate. Simultaneous opens are tiebroken by open time — without that, two tabs would each object to the other and *both* would lock out.
- Access tokens are forwarded as `Bearer` on every API call. Auth helpers (`lib/auth/`) handle login/register, Zod validation, and in-memory rate limiting.

### API Client

`lib/api/client.ts` — base `apiClient` with `get/post/put/patch/delete`. Mutating methods and many reads **automatically inject `lg: "en"` into the request body** (a backend convention); several logical GETs are implemented as POST.

**The base URL is resolved per environment**, because `apiClient` is imported from Client *and* Server Components (`app/dashboard/layout.tsx` → `billingApi.getStatus`, `app/dashboard/page.tsx` → `postsApi.list`). On the server it prefers `FEEDBOARD_API_BASE_URL` (an internal address in a containerised deploy) and falls back to the public one; in the browser only `NEXT_PUBLIC_FEEDBOARD_API_BASE_URL` exists. Reading *only* the public var on the server means every server-rendered page hairpins out to the public hostname and back through the proxy — slower, and it makes server rendering depend on the API's public TLS cert being valid (an invalid cert on the API subdomain took the dashboard down server-side while browser calls were unaffected). `lib/api/public.ts` and `lib/auth/server-config.ts` follow the same precedence; `lib/avatar.ts` deliberately inverts it (its output goes into `<img src>`, so it must be the public origin even server-side).

Services live in `lib/api/` and are re-exported from `lib/api/index.ts`:

```typescript
import {
  postsApi, votesApi, commentsApi, roadmapApi, changelogApi,
  notificationsApi, tagsApi, analyticsApi, usersApi, tenantsApi,
  apiKeysApi, auditLogsApi, integrationsApi, uploaderApi, publicApi,
  extractRows, extractTotal, parseJsonField,
} from "@/lib/api";
```

Authenticated services take an `accessToken` from `session.user.accessToken`. The helpers `extractRows / extractTotal / parseJsonField` normalize the backend's varied response shapes. `publicApi` (unauthenticated server fetch) and `uploaderApi` (multipart, no JSON `lg` body) bypass the standard client.

### Billing & subscriptions

> **`BILLING_CHECKS.md` (project root) is the billing regression checklist.** Every
> item in it is a bug that actually shipped — an advertised price that wasn't the
> charged price, a promo redeemable forever, a "3-month" offer that never expired.
> They were all invisible from the UI. **Run it after any billing change, after
> switching `PADDLE_ENV`, and before going live**, and verify against real Paddle
> transactions rather than a script's `OK` output.

- **Payment provider — Paddle (active) or Stripe (dormant).** The active provider is chosen by **`BILLING_PROVIDER`** (backend) / **`NEXT_PUBLIC_BILLING_PROVIDER`** (client), default **`paddle`**. Paddle is a **Merchant of Record** (needed because Stripe can't pay out to Bangladesh); Stripe's implementation is kept intact and re-selectable with `=stripe`. Both are provider-agnostic behind a seam — the account model, Billing-tab UX, cancel-at-period-end/resume, and admin comps are unchanged. **Checkout differs by provider**: Paddle returns `{ transactionId }` → the client opens the **Paddle.js overlay** (`lib/paddle.ts`, `@paddle/paddle-js`); Stripe returns `{ url }` → redirect. Plan changes are in-app: **upgrades** charge the prorated difference now (the preview's `amountDueNow` is `immediateTransaction.grandTotal`, verified == the actual charge and confirmed to credit already-paid time). **Downgrades are scheduled to the end of the current paid period** — the customer keeps their current (higher) plan until period end, then the lower plan applies, with **no charge and no refund** (matches the "keep current plan until period end" policy). Paddle has **no native scheduled plan change** (`scheduledChange` only does pause/cancel/resume; `prorated_next_billing_period` *rejects* interval changes), so a downgrade switches the Paddle item **now** with `do_not_bill` (verified: no charge/refund, billing date preserved → the next renewal auto-bills the lower price) while the account's **in-app plan stays at the higher tier until `current_period_end`** via the `pending_plan/pending_interval/pending_effective_at` markers; `reconcile` (in `paddleBilling.js`) is pending-aware — it holds the higher plan until the effective date, then flips to the lower one and clears the markers. **Cancel change** (`cancelScheduledChange`) switches the Paddle item back to the higher plan (`do_not_bill`) and clears the markers. **No interval change off a yearly plan is offered.** A yearly subscriber keeps the year they paid for; monthly becomes available once that year ends and they are no longer subscribed. The client shows a disabled `billing.switchAfterYearly` ("Available when your yearly plan ends") on the monthly toggle — for the same-tier switch *and* a tier downgrade that would also shorten the interval — and `applyChange` rejects any interval change away from yearly with `downgrade_interval_unsupported` rather than trusting the client. A downgrade that *lengthens* the interval (monthly→yearly) is likewise not offered: change the tier first. Same-tier monthly→yearly is an upgrade and is unaffected. The deferred machinery (`pending_*` + `applyDuePendingChanges`) still exists and drives same-interval downgrades at period end; the interval-changing path is simply not reachable. "Manage billing" still opens the Paddle portal for card updates. **Payment methods are not configured in code** — `openPaddleCheckout` sets **no** `allowedPaymentMethods`, so the buyer sees whatever is enabled in the **Paddle dashboard** (Checkout → Payment methods) *and* is eligible for that transaction. Eligibility is decided by Paddle, not us: the buyer's **device/browser** (Apple Pay → Safari + a Paddle-**registered domain** over HTTPS, so it never shows on localhost; Google Pay → Chrome + saved card; Samsung Pay → Samsung device), **country/currency** (iDEAL/Bancontact = EUR, BLIK = PLN, Pix = BRL, Korean methods = KRW, etc.), and **whether the method supports a recurring subscription** (several one-time-only methods — e.g. WeChat Pay — never appear on our subscription checkout regardless of dashboard state). So for a USD subscription on desktop the realistic set is **card, PayPal, and Google Pay** (+ Apple Pay in production Safari). To offer more, enable them in the dashboard and match the buyer's currency — there is nothing to change in this repo. The overlay (`openPaddleCheckout`) uses `variant: "one-page"` to surface wallet express buttons, and sets `showAddTaxId:false` + `showAddDiscounts:false` to keep it minimal — no "Add VAT number / ABN" tax-ID field and no Paddle "Add discount" field (promo codes are redeemed in our Billing tab and applied server-side by discount id, so Paddle's field is redundant). The in-overlay copy ("redirecting to PayPal", "contacting the bank", …) is Paddle's hosted UI and **not customizable from our code**. **Promo codes + promotional offers work on Paddle** (Phase 2): they're backed by a **Paddle discount** (offer = a `flat` amount-off discount; percent-off promo = a `percentage` discount) created when the admin makes the offer/code and **auto-applied at checkout by `discount_id`** on the server-created transaction — never a code typed into the overlay, so the buyer pays the discounted price exactly (sandbox-verified: $2.50-off offer and 25%-off code both applied to the cent). The display (strike-through/SAVE badges, "Have a promo code?" field) is provider-agnostic and shown on both providers. Client env: `NEXT_PUBLIC_PADDLE_CLIENT_TOKEN`, `NEXT_PUBLIC_PADDLE_ENV`.
- Three tiers — **Free / Pro / Business**, billable **monthly or yearly** (yearly is 20% off — `YEARLY_DISCOUNT` in `lib/plans.ts`, mirroring the backend). Pro and Business carry a merchandising pill beside the plan name (**Popular** / **Best**) via `PlanDisplay.badgeKey`; it is always shown, unlike the price "SAVE X%" badge which depends on the active offer/interval. It replaced the old conditional "Recommended" badge. The display config (numeric `monthlyPrice`, feature bullets, highlight) lives in **`lib/plans.ts`**; `planPricing(plan, interval)` derives the shown price (yearly shows the discounted per-month equivalent + "billed annually ($X/yr)"). It's the single source of truth for both the dashboard Billing tab and the public pricing page. The enforced limits + Stripe Price IDs (monthly **and** yearly) live on the backend (`src/consts/plans.js`); `lib/plans.ts` is presentation-only.
- **Monthly/Yearly toggle** — `components/pricing/interval-toggle.tsx` (shared). The **public** pricing page splits into a server wrapper (`pricing-section.tsx`, fetches offers) + a client `pricing-cards.tsx` that owns the toggle. The **Billing tab** (`billing-settings.tsx`) has the same toggle and passes `interval` to `billingApi.checkout(plan, token, { interval, promotionCode })`. An admin promotional **offer** (diagonal-strike) can target **either** the monthly or the yearly price (see Offers below); when no offer covers the toggled interval, yearly shows its built-in 20%-off price with a "Save 20%" badge. The toggle's generic **"Save 20%" badge is hidden when any yearly offer is active** (`IntervalToggle` `showSave={false}`) so it doesn't contradict the per-plan offer discount. `billingApi.getStatus().billingInterval` (`'month'|'year'|null`) drives the "Billed yearly/monthly" line on the current-plan card. The card also shows a **renewal/end note** from `currentPeriodEnd` + `cancelAtPeriodEnd`: a renewing subscription reads "Renews on `<date>` — you'll be charged again then"; one set to cancel reads "Your subscription ends on `<date>` — no further charges"; a comped plan reads "Complimentary access until `<date>`" (timed) or "…no expiry" (lifetime). `cancelAtPeriodEnd` is read **live from Stripe** in `getBillingStatus` (non-fatal; the DB doesn't persist the cancel flag).
- **Hosted Stripe Checkout + Customer Portal** — no card data touches this app. `lib/api/billing.ts` (`billingApi.getStatus / checkout / portal`) calls the backend, which returns a Stripe URL; the client just `window.location.assign`es to it.
- **Billing settings tab** (`components/settings/billing-settings.tsx`, admin-only) shows the current plan + a 3-card grid. Free users get **Upgrade** (→ Checkout, a fresh subscription). **Subscribers change plan IN-APP with proration** (not via the Portal): the card CTA is **Upgrade/Downgrade to X** (or **Switch to yearly/monthly** for the same tier, different interval). It opens a confirm dialog that first calls `billingApi.changePreview` and shows the **exact prorated charge** — *"You'll be charged $X now"* for an **upgrade** (only the difference; already-paid time credited), or *"takes effect on `<date>`, no charge now"* for a **downgrade** (scheduled at period end). Confirm → `billingApi.changePlan`. A pending downgrade shows a banner with **Cancel change** (`billingApi.cancelChange`). **Manage billing** (→ Portal) stays on the current-plan card for card updates. **Cancel subscription** is **in-app** (no Portal needed): a subtle link opens a confirm dialog → `billingApi.cancelSubscription` → `POST /billing/cancel` sets Stripe `cancel_at_period_end` (owner keeps the plan until `currentPeriodEnd`, no further charge, then reverts to Free via the webhook/reconcile). While set to cancel, the card's period note reads "ends on `<date>`" and the button becomes **Resume subscription** (`billingApi.resumeSubscription` → `POST /billing/resume`, clears the flag). Comped accounts have no Stripe sub, so neither control shows. `changeDirection()` mirrors the backend's upgrade/downgrade rule (rank by plan tier, then month<year). Stripe Checkout returns to `?tab=billing&checkout=success|cancelled`.
- **Public pricing**: `components/pricing/pricing-section.tsx` is rendered on the landing page (`#pricing`) and a dedicated `app/pricing/page.tsx`.
- **Buying from the pricing page.** A paid CTA carries the intent as **one encrypted token, `?c=<token>`** — never readable `?plan=&interval=` params. `lib/plan-intent-token.ts` (**server-only**) seals `{plan, interval, expiry}` with **AES-256-GCM** keyed off `AUTH_SECRET`; `lib/plan-intent.ts` holds only the shape + link builder, so it stays safe to import in a Client Component. GCM is authenticated encryption, so one primitive covers both needs: the payload can't be **read**, and a tampered token fails the auth tag and decrypts to nothing rather than silently changing what we charge for. The payload is **fixed width** (one char per field + a zero-padded 13-digit expiry) on purpose — GCM ciphertext is the same length as its plaintext, so spelling out `business` vs `pro` would leak the plan through token *length*. A random IV means the same intent yields a different token each time. Tokens expire after **7 days** and are **re-signed at every hop**, so one can't outlive its TTL by being passed along. Be honest about the limit: with only four possible intents, anyone can click all four buttons and learn the mapping for their own session — this protects the URL's contents, not the fact that a plan was chosen. Price is **never** in the token; it's resolved server-side at checkout, so a stale link can only preselect a plan, never a stale price. **A token that doesn't verify means no intent** — the same graceful path as arriving at `/signup` directly, which is also what happens to old plaintext `?plan=pro` links (they no longer preselect anything; that's the point). Because the secret is server-side, **each hop's `page.tsx` is a Server Component** that decodes and passes the result down — `app/onboarding/onboarding-form.tsx` and `app/checkout/checkout-form.tsx` are the client bodies; `PricingSection` mints all four tokens up front (`planIntentTokens()`) because the interval toggle is client-side and signing isn't. Flow: pricing → `/signup` → `/onboarding` → **`app/checkout/page.tsx`** → dashboard. Checkout sits *after* onboarding by necessity, not preference: `POST /billing/checkout` requires `role === "owner"` and a fresh signup has no workspace, so creating one is what makes checkout reachable at all. A signed-in visitor skips ahead (owner → checkout, otherwise → onboarding); an **invited** user drops the intent entirely, since they become a *member* of someone else's workspace and members can't buy. The checkout page guards in order — unauthenticated → login, no workspace → onboarding, non-owner → dashboard, invalid/`free` plan → dashboard, existing subscription → Billing tab — and shows **"Taxes calculated at checkout", never a "Total today" figure**: Paddle is Merchant of Record and adds tax we don't compute, so a concrete total here would be exactly the advertised-vs-charged bug `BILLING_CHECKS.md` exists to catch. Abandoning checkout is harmless (the workspace already exists), which is why "Continue on the Free plan" is offered rather than hidden.
- **Yearly is the default interval** on the pricing cards and checkout. The **Billing tab defaults to the subscriber's OWN `billingInterval`** when they have one — a flat yearly there would show a monthly subscriber yearly prices and "switch" CTAs against their own plan, reading as though we'd changed their billing. Offer strike/per-month/percent math lives **once** in `lib/plans.ts` → `offerDisplay()`, used by the pricing cards, the Billing tab and checkout; never re-derive it inline (duplicated pricing arithmetic is how "advertised $5.60, charged $10" happened).
- **Subscriptions are per ACCOUNT, not per workspace.** A user pays once and the plan covers **every workspace they own**. The backend source of truth is `billing_accounts` (keyed by email); it's mirrored onto each owned `tenants.plan_name` so all plan reads are unchanged. The Billing tab (`billing-settings.tsx`) is account-scoped — it manages the one account subscription no matter which owned workspace's Settings you open it from, and shows a note that the plan "applies to your whole account" (`billing.accountWide`). A **new workspace inherits the account plan** at creation (a Business account's new board is Business immediately). Seats stay **per workspace**.
- The **plan is set by Stripe** (checkout + webhook) **or by an admin comp** (Admin Panel **Accounts** view / free-plan promo). A comped plan carries `subscription_status='comped'` with no Stripe subscription; the backend reconcile guard preserves it. `planName` was dropped from `UpdateTenantData` — clients can't change their plan directly. A Free workspace that tries a paid capability (deleting feedback, attachments, contacting submitters, …) gets a `402` with an upgrade message, surfaced as a toast.
- **Admin plan grant (comp) is per account.** The Admin Panel **Accounts** view (`app/admin/accounts/page.tsx`, `adminApi.listAccounts` / `setAccountPlan`) lists billing accounts (email + owned workspaces + plan); picking Pro/Business opens a **duration dialog** (Lifetime / 1 / 3 / 6 / 12 months) → `PUT /admin/accounts/:email/plan {plan, durationMonths}`. Backend comps the whole account (**cancels any live account Stripe subscription first**), mirrors onto every owned workspace, with `current_period_end` = NULL for lifetime or `NOW()+N months` timed (reconcile reverts an expired timed comp to Free). Revoking to Free applies immediately. The Admin **Workspaces** list (`app/admin/workspaces/page.tsx`) now shows the plan **read-only** (set it in Accounts).
- **Offers (monthly *or* yearly).** Admins set a promotional **price** on Pro/Business for a chosen **billing cycle** (Admin Panel → Offers picks plan + Monthly/Yearly). An offer is scoped to `plan` + `interval` (one active per pair): a monthly offer discounts the monthly price, a yearly offer discounts the yearly **total** (e.g. $80/yr off the $96/yr list). Offer prices may be **fractional** ($7.50); the backing provider discount is a fixed amount-off (list − offer) so checkout charges the offer price exactly — a **Stripe coupon** `amount_off` or, on Paddle, a **`flat` discount** (`recur:true`, restricted to that plan+interval's price) applied by `discount_id` on the transaction. `getStatus().offers` / `getOffers()` are keyed **`offers[plan]?.[interval]`** (`OfferMap`): the Billing tab and public pricing cards read the offer for the **currently-toggled interval** and, when present, draw the list price with a **diagonal** rose strikethrough (a `linear-gradient` line) + the green offer price + a "SAVE X%" badge. **The headline figure is always per-month (`/mo`), on both intervals — never headline the yearly total.** On a **yearly offer** the struck price is the plain **monthly list price** (`plan.monthlyPrice`, e.g. `$10`) and the offer price is `offerPrice / 12` (`$5.60`): an offer **replaces** the built-in 20% yearly discount rather than stacking on top of it, so the comparison is against the standard monthly rate. The "SAVE X%" badge is therefore **recomputed from the two displayed figures** (44%) rather than taken from the backend's `percentOff` (30%, which is measured against the already-discounted yearly list) — otherwise the badge contradicts the prices beside it. The note beneath is just "billed annually", with **no** annual total. Checkout auto-applies the matching-interval coupon server-side. **On Paddle an offer must be applied in three places, because a discount attached to one thing does not propagate to the others:** (1) the **checkout transaction** (`createCheckout` → `discountId`), which discounts the first payment; (2) the **subscription** created from it — Paddle does *not* copy the transaction discount across, so the checkout reads "$5.60 now, then $10.00/month" and the customer would jump to list price at renewal. `reconcile` therefore calls `ensureOfferDiscount` to attach the offer to the subscription (`effectiveFrom: "next_billing_period"`, since the first period was already discounted); and (3) **plan changes** (`previewChange`/`applyChange` → Paddle's `discount` field), since our offer discounts are `restrictTo` a single price and cannot carry from the old plan — without this, "Pro yearly $4.48/mo" was quoted at the $96 list price. The **public pricing page** (`components/pricing/pricing-section.tsx`) shows the same via `publicApi.getOffers()` → unauthenticated `GET /public/offers`.
- **How long an offer price lasts.** An offer's **window** (`starts_at → ends_at`) is both how long it's on sale *and* how long a buyer keeps it, via the Paddle discount's **`maximumRecurringIntervals`** (`offerDurationPeriods()` in `common/offers.js`, exposed to the client as `durationPeriods`): a **monthly** offer lasts one period per month of the window (a 3-month offer = 3 charges at the offer price, then the regular price); a **yearly** offer is always **1** — a billing period *is* a year, so the buyer gets the offer price for that whole year. An open-ended monthly offer (no `ends_at`) recurs forever. Both cards say what happens next (`pricing.offerForMonths` / `offerFirstYear` → *"Offer price for the first 3 months, then $10.00/mo"*) so a time-limited price never reads as permanent. **An active offer is the plan's CURRENT price, not a new-customer deal** — `ensureOfferDiscount` applies it to **any** active subscription on that plan+interval, so an existing subscriber renewing during the window is billed the offer price too (surfaced on the current-plan card as `billing.offerAppliesToRenewals`); billing a loyal customer $10 while advertising $5.60 on the same page isn't defensible. It never overrides an existing discount, so someone on a promo code or an earlier offer keeps their terms. **Known, accepted imprecision:** a subscriber picked up mid-window gets the full N periods from when the discount attaches, so their discount can run slightly past the window's end. Paddle counts billing periods, not calendar dates, and one shared discount has one fixed limit — being exact would need a per-subscriber discount plus a removal pass, i.e. new machinery whose bugs either overcharge someone or discount forever. Bounded and generous beats exact and fragile here; don't "fix" it without that trade in mind.
- **Re-minting offer discounts.** `scripts/backfill-offer-discounts.js` creates the provider discount for active offers that lack one, and `--force` re-creates them (**required after switching `PADDLE_ENV`**, since discounts don't exist across environments). It reads `starts_at`/`ends_at` to set the period limit — omitting them silently produces a **forever** discount, which is the expensive direction to get wrong, so verify `maximumRecurringIntervals` on the created discounts rather than trusting the script's `OK` output. Re-minting leaves the previous discounts **active but unreferenced** in Paddle; archive the orphans, since an active discount is applicable by id.
- **Promo codes.** Admins generate codes in the Admin Panel; owners redeem them in the Billing tab's "Have a promo code?" field (`billingApi.redeem`). A **free-plan** code comps the plan instantly (the comped status renders as "Active" in the Billing tab so it never reads as charity) — like the admin comp path, redeeming it **cancels any live Stripe subscription and clears `stripe_subscription_id`** first, so Stripe doesn't keep charging a workspace whose plan is now comped (`reconcileTenantSubscription` skips comped tenants, so an un-cancelled sub would bill forever). A **percent-off** code stores a Stripe promotion code that the next `billingApi.checkout(plan, token, promotionCode)` applies as a discount (checkout keeps `allow_promotion_codes` when no code is passed, so users can also type one at Stripe Checkout). A code's **`applies_to_plan`** restriction is enforced **server-side at checkout** (`createCheckoutSession` looks the promo up by `stripe_promotion_code_id` and rejects with `promo_plan_mismatch` when the code is scoped to a different plan than the one being purchased) — necessary because the Stripe coupon behind a percent-off code carries no product restriction, so the DB scope is the only gate. **On Paddle** the same flow is backed by a Paddle `percentage` **discount** (created by `admin/promo.js` via `common/discounts.js`, `restrictTo` the plan's prices when scoped); `redeemPromo` returns its `paddle_discount_id`, and `paddleBilling.createCheckout` applies it via `discountId` on the transaction and performs the **same `applies_to_plan` re-check** → `promo_plan_mismatch`. Free-plan comp codes are **provider-agnostic** (the comp path cancels any live sub on the active provider, then comps the account). **A code is redeemable once per ACCOUNT (email), for both code types, enforced by the database** — `promo_redemptions.account_email` + `UNIQUE (promo_code_id, account_email)`, so a duplicate fails with `ER_DUP_ENTRY` → `promo_already_redeemed` even if two requests race. The **global** cap (`max_redemptions`) is claimed atomically (`UPDATE … WHERE times_redeemed < max_redemptions`), so only one of N concurrent callers takes the last slot; set `max_redemptions = 1` for a code that may be used exactly once in total. Both types record a redemption — percent-off codes previously recorded nothing, so they were infinitely reusable and never hit their cap. A comp that fails *after* claiming releases the claim so the customer doesn't lose their redemption to our error.
- **Multiple devices** (`limits.multiDevice`) is **Business-only** — Free and Pro are one-device-at-a-time. See the device-sessions bullet under *Authentication & session*.
- **Feedback attachments** (`limits.attachments`) are a **Pro+** capability: a feedback post can carry up to **3 photos or short videos** (images ≤10MB; video ≤50MB, capped by size not duration). Two upload surfaces share one flow — upload first, then link the returned ids on submit:
  - **Public board** (`components/portal/feedback-submit.tsx`): a *guest* can attach when the workspace is paid. The portal page passes `attachmentsEnabled` from `publicApi.getTenant().attachments_enabled` (the public tenant read exposes only the boolean, never the plan). Uploads go to `uploaderApi.uploadPublicAttachment(file, tenant)` → unauthenticated `POST /public/:tenant/attachments`; the submit body carries `attachmentIds`.
  - **Dashboard** (`components/feedback/create-post-dialog.tsx`): the dialog reads `billingApi.getStatus().limits.attachments` on open; on Pro+ it shows the picker (Free shows an inline “Upgrade to Pro” hint). Uploads go to `uploaderApi.uploadAttachment(file, token)` → authenticated `POST /posts/attachment`; `attachmentIds` ride on `postsApi.create`.
  - Shared UI: **`components/feedback/attachment-picker.tsx`** (upload/preview/remove, client-validates type+size via `lib/attachments.ts`) and **`components/feedback/attachment-gallery.tsx`** (image grid + lightbox, inline `<video controls>`), rendered on both post-detail pages. Board cards show a 📎 count. Attachment paths are backend-relative — always run them through `resolveUploadUrl`. The plan gate runs **server-side before multer**, so a Free workspace never streams a rejected file; the id-linking is tenant-scoped so an attachment can't be claimed onto another workspace's post.
- **Upvoting is public-board-only.** Votes are a signal *from a workspace's users*, so the workspace's **own owner/team cannot vote** — the dashboard board card and feedback detail render the vote as a **read-only tally** (`vote_count`), never a button. Only `components/portal/portal-vote-button.tsx` (→ `POST /public/:tenant/posts/:id/vote`, guest-id/account identified) casts a vote. Enforced by construction rather than by a role check: the authenticated add/remove vote endpoints were **removed** (`/votes` is now read-only — `POST /votes/post/:postId` survives), and `votesApi` has no `add`/`remove`. Don't reintroduce a dashboard vote control — it would inflate a tenant's own numbers.
- **Reject / restore feedback.** The dashboard board (`components/feedback/feedback-list.tsx`) has a **Rejected** tab. On the **Open** tab, the bulk selection bar offers **Reject** next to **Send to Roadmap** (sets the selected posts' status to `rejected` via `postsApi.updateStatus`). Rejected posts still appear in the **All** tab (and their own Rejected tab), but are hidden from the **public board + post detail** entirely (always excluded server-side). From the **Rejected** tab, a bulk **Restore to Open** brings them back; a rejected post's **detail page** shows a "Restore to open" button instead of the status dropdown. `rejected` is a real `posts.status` enum value (distinct from the legacy, unused `closed`); `updatePostStatus` validates against the allowed set.
- **Contact & notify submitter** is an **owner-only, Pro+** capability (`limits.contactSubmitter`). On a post's detail page (`app/dashboard/feedback/[id]/page.tsx`) a Pro+ owner sees the **submitter's email** (backend `getPostById` returns `author_email` as `null` on Free, so it never reaches the client), and when the post is **Completed** a **"Notify: implemented"** button emails the submitter that their feedback shipped (`postsApi.notifyImplemented` → `POST /posts/:id/notify-implemented`; a branded `feedbackImplementedEmail`). The send is recorded (`implemented_notified_at`) so the card shows "✓ Implemented email sent …" and the button becomes **Resend**. A Free owner sees a locked upsell instead. Enforced server-side (`402` on Free, `400` unless completed / when no submitter email).
- **Deleting feedback** is an **owner-only, Pro+** capability. The dashboard feedback detail (`app/dashboard/feedback/[id]/page.tsx`) only renders the Delete control for the `owner` role; it reads `billingApi.getStatus().limits.deleteFeedback` and, on Free, shows a locked button that toasts an **Upgrade** action (→ `settings?tab=billing`) instead of deleting. Enforced server-side (`deletePost`: `403` non-owner, `402` on Free). Comments/replies are unaffected.
- No client-side Stripe key is needed (hosted Checkout only redirects to a backend-provided URL).

### Design System

**Light-only app.** A `prefers-color-scheme: dark` media query was removed and `color-scheme: light` is forced in `globals.css`. Do not reintroduce dark-mode variants — the app hardcodes light brand colors, so dark tokens make shadcn components unreadable.

Brand colors:
- Primary: `#c74959` (rose) · Secondary: `#da6a78` · Accent/border: `#e399a3` · Background: `#fdf8f9` · Text: `#1c0a0c`

Typography: **Inter for headings, Sora (sans) for everything else.** Mono (JetBrains) is reserved for code, API keys and metadata (vote counts, status labels, section eyebrows).

- **Every face must request `subsets: ["latin", "latin-ext"]`.** Polish (`ą ć ę ł ń ś ź ż`) and the rest of Latin Extended-A are **not** in the `latin` subset. This was wrong for a long time — Sora carries all body copy and only requested `latin`, so the entire `pl` locale rendered those glyphs in a fallback system font, mid-word, in every heading and paragraph. Verified per-character against the loaded face, not assumed. Any new font added here needs the same pair.

- **All three faces are declared in `lib/fonts.ts`, and swapping one is a ONE-LINE edit** — change the aliased identifier in its import (`Fraunces as DisplayFace` → `Playfair_Display as DisplayFace`) and nothing else. The aliases are what make this work: `next/font/google`'s build-time transform resolves the imported name, so downstream code refers only to `fontDisplay` / `fontSans` / `fontMono` and the CSS refers only to the `--font-brand-*` variables. **Never re-introduce a `next/font` call in `app/layout.tsx`** — it takes `fontVariables` from this module, and putting a second declaration there is what made the last font change a three-file edit. The file also lists vetted alternatives that pair with Sora.

- **Where the serif applies.** `--font-heading` → `--font-brand-display` (Fraunces, loaded in `app/layout.tsx`), so every `font-heading` consumer picks it up: dialog, alert-dialog, sheet, drawer, popover and card titles, plus the auth pages. A base-layer rule in `globals.css` additionally sets **`h1, h2`** in the display face, which is what reaches the ~20 dashboard/admin/portal page titles without editing each file. The **`FeedBoard` wordmark** uses `font-display` in all five places it appears (landing nav + footer, pricing nav, checkout, onboarding, dashboard sidebar) — it's a brand lockup and must not drift between surfaces.
- **Where it deliberately does NOT apply.** Body copy, form controls, buttons, table data — and **`h3` and below**, which title rows in dense lists (feedback posts, comments). A display serif in a form field or a scannable list is a downgrade, not an upgrade. Override with `font-sans` if a specific `h1`/`h2` needs it.
- **Display-face axes** live in a single custom property, `--font-display-axes` in `globals.css` — the only CSS a font swap might touch, and only if the new face has axes worth setting (a face without them ignores the value; `normal` opts out). Fraunces' `SOFT`/`WONK` are what keep it warm rather than the neutral high-contrast serif every generated page reaches for. **`opsz` is deliberately not listed** — naming the axis freezes it, whereas `font-optical-sizing: auto` lets it track the rendered size, so a 16px dialog title and a 68px hero headline are each drawn as designed. That rule also carries **no `letter-spacing`**: it would out-rank Tailwind's `tracking-*` utilities (same specificity, later in source order) and silently break them, so per-element tracking is set on the element.
- **Landing-only colour**: evergreen `#2f6b53` marks *shipped* in the hero's `RequestLifecycle` and nowhere else in the app. It's the single cool note in the warm palette, which is what makes the status sequence read as a system rather than decoration. The rest of the page is the standard rose set.
- **Landing motion budget is one orchestrated moment** — the hero's `components/landing/request-lifecycle.tsx`, where a single request walks Open → Planned → In Progress → Shipped and stamps a trail. There are deliberately **no** scroll-reveal or lift-on-hover effects elsewhere on the page; scattered micro-animation is a large part of what makes a page read as generated. `lp-`-prefixed keyframes in `globals.css` are scoped to this surface and are disabled under `prefers-reduced-motion` (the component then jumps straight to the resolved state, which is the one that carries the meaning).

Conventions:
- Dialogs & alert-dialogs are glossy white (white→`#fdf8f9` gradient, soft shadow, rose ring); backdrop is `bg-[#1c0a0c]/30` blurred. `Select` dropdowns default to `position="popper"`.
- Form fields (Input / Textarea / Select trigger): white bg, soft rose border, rose focus ring, `h-10`.
- Buttons: filled primary = `bg-[#c74959]`; the `outline` and `ghost` variants have a rose hover (`hover:bg-[#c74959]/10 hover:text-[#c74959]`).

### Rendering & performance

- The single `AuthSessionProvider` (root `app/layout.tsx`) is **seeded server-side** via `await auth()` so authenticated pages have the session/token on first paint. Without the seed there's a loading gap where the dashboard fires token-less API calls and the backend replies plain-text `Access denied`. Every route is already dynamic (auth/portal reads), so seeding costs no static rendering.
- `lib/api/client.ts` reads each response as text then `JSON.parse`s defensively — non-JSON error bodies (like `Access denied`) become a clean `ApiError`, not a misleading "can't connect".
- Authenticated surfaces (dashboard, login/signup, landing) read the session/cookies and are **dynamic by design** — don't try to force them static.
- The **public portal is dynamic** because its backend reads are POST and Next's Data Cache only caches GET. `app/portal/[tenant]/layout.tsx` already sets `export const revalidate` (activates once those reads become GET + `next: { revalidate }`); until then `loading.tsx` provides streaming. `publicApi.getTenant` is wrapped in React `cache()` to dedupe the tenant lookup per render.
- Route transitions stream via `loading.tsx` skeletons (`app/dashboard/`, `app/portal/[tenant]/`).
- Remote images use `next/image`; allowed hosts are in `next.config.ts` → `images.remotePatterns`.
- Heavy libs in `components/ui/` (recharts, @tanstack/react-table, cmdk, react-day-picker, …) are scaffolding **not imported by any route**, so they're tree-shaken out of bundles. Don't import them into a route without weighing the bundle cost.

### Environment Variables

```
AUTH_SECRET                        # NextAuth secret
AUTH_URL                           # Canonical public origin w/ protocol — REQUIRED behind a proxy
FEEDBOARD_API_BASE_URL              # Server-side API URL (default: http://localhost:4560)
NEXT_PUBLIC_FEEDBOARD_API_BASE_URL  # Client-side API URL (same)
NEXT_PUBLIC_ROOT_DOMAIN            # Root domain for subdomain routing (default: localhost:3000)
NEXT_PUBLIC_FEEDBACK_SUBDOMAIN     # Subdomain of FeedBoard own feedback board (default: feedback)
NEXT_PUBLIC_BILLING_PROVIDER      # Active payment provider: paddle (default) | stripe
NEXT_PUBLIC_PADDLE_CLIENT_TOKEN   # Paddle.js client token (sandbox: test_…, prod: live_…)
NEXT_PUBLIC_PADDLE_ENV            # sandbox | production (must match the client token)
```

**`AUTH_URL` is required in any reverse-proxied deployment** (Nginx, Dokploy/Traefik) and omitted in local dev. NextAuth builds every redirect it issues — sign-out `callbackUrl`, post-login `callbackUrl`, `?error=` pages — from `reqWithEnvURL()` (`next-auth/lib/env.js`), which consults **only** `AUTH_URL`/`NEXTAUTH_URL` and otherwise passes the request through untouched. Behind a proxy the request's origin is the container's internal address, so with it unset, signing out redirects to **`https://localhost:3000/...`**. `trustHost: true` (set in `auth.ts`) governs host *trust*, not this URL construction — it does not substitute. Not a `NEXT_PUBLIC_` var, so it's read at runtime: setting it needs a restart, not a rebuild.

Configured in `.env.local` (not committed). **`.env.example` is the committed template** — copy it. Full list + host setup in **`DEPLOYMENT.md`** (Hostinger VPS: Nginx wildcard-subdomain reverse proxy, PM2, MySQL, wildcard TLS, Stripe webhook).

The **`dev` script** raises the Node heap (`cross-env NODE_OPTIONS=--max-old-space-size=4096 next dev`) so the dev server's memory-threshold auto-restart (Next recycles the worker past 80% of the heap limit during long editing sessions) triggers far less often. Production (`build`/`start`) is unaffected.
